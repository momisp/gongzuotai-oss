---

## 0. 一句话结论

你们的面板不是「又一个 TestOps」，而是**业务钱链路的混合编排驾驶舱**：SDK + 表单 + SQL + Playwright +（可选）Apifox CLI，强绑定龙翔/游趣/汇玩与分佣结算语义。

相对市面「先进自动化平台」：

| 维度 | 相对位置 |
|------|----------|
| **业务语义 / 混合引擎编排** | 明显领先多数通用 TestOps（它们不懂 `promote_ratio` / 结算期 / 打款门禁） |
| **观测驾驶舱（总览形态）** | 已接近中小团队自建看板水平（对齐 996 出包石板思路） |
| **用例资产 / 并行调度 / CI 生态 / 缺陷闭环** | 明显落后成熟 TestOps / CI Dashboard |
| **失败调试深度（Trace / 视频 / Flaky）** | 刚起步（有步骤截图与 HTML 报告，无 Trace/视频/根因聚合） |
| **产品化与协作** | 本机工作台门面，非多租户 SaaS |

**建议定位**：继续做「游戏分发业务自动化总控」，用市面平台补「通用测试基建」；不要用半年去仿 Allure TestOps 全功能。

## 1. 我们现在是什么（能力快照）

### 1.1 已具备（相对 PRD 已推进）

| 能力块 | 现状 |
|--------|------|
| 入口与总览 | 独立页；排队 / 当前执行 / 今日成败 / 吞吐 / 运行情况 / 风险日历 |
| 编排 | 单槽队列；档 A（至分佣）、档 B / 一键主链（至提现含打款开关） |
| 混合引擎 | SQL 种子、SDK 注册下单、回调、SQL 断言、PW 总后台、会长表单 |
| 业务参数 | 游戏 / 会长 / 充提金额 / 登录账号等展示与回填 |
| 分支补洞 | S0 未申请游戏可自动 F5 申请 |
| 证据 | 步骤断言表、run.log、自研 HTML 报告、PW 步骤截图（S7/S10/S11） |
| 健康 | 3780 回调、Apifox token、stub 计数等告警 |
| 接线诚实度 | wired / stub 可见；遇 stub 停，不假绿 |

### 1.2 明确非目标（首版 PRD）

不重做 Apifox/PW/Airtest 编辑器 · 不接财务流水核验 · 不默认无人真打款 · 不做多机集群大屏。

这些「非目标」本身就划定了与市面平台的边界——对比时要按「业务总控」评，不能按「企业级 TMS」硬刚。

## 2. 市面参照系（按类型，不是按品牌撕）

| 类型 | 代表 | 解决什么 |
|------|------|----------|
| **A. TestOps / TMS** | Allure TestOps、Qase、qTest、MeterSphere | 用例库、计划、Launch、趋势、缺陷联动、权限 |
| **B. CI 执行看板** | Currents、TestDino、BrowserStack Analytics | 并行跑结果、Flaky、Trace/视频、PR 视图 |
| **C. 执行基建** | Selenium Grid、BrowserStack、云真机 | 多浏览器/真机池、并发、设备矩阵 |
| **D. 接口自动化 IDE** | Apifox、Postman、JMeter 管控台 | 场景编排、环境变量、数据集、报告 |
| **E. 自建流水线** | Jenkins/GitLab CI + Allure Report | 触发、制品、报告归档 |

你们更接近：**E 的看板 + D/B 的局部执行能力 + 强业务 DSL**，而不是完整 A。

## 3. 分维度差距对比

评分口径（对本面板）：

- **●●●●●** 达到或超过同类产品在该维度的主流水准  
- **●●●○○** 可用，缺深度或规模  
- **●●○○○** 有雏形 / 脚手架  
- **●○○○○** 基本缺失  
- **—** 非目标或不适用  

### 3.1 产品定位与范围

| 对比项 | 市面先进平台 | 我们 | 差距 |
|--------|--------------|------|------|
| 产品形态 | 多租户 SaaS / 私有化 TMS | 工作台本机门面 | 协作与部署形态落后 ●○○○○ |
| 定位清晰度 | 「测管」或「跑测分析」 | 「业务钱链路总控」 | **定位更准**（业务向） ●●●●○ |
| 覆盖广度 | 全项目、多端、手动+自动 | 首条主链（充值→提现） | 广度窄 ●●○○○ |
| 领域深度 | 通用断言 / 通用 UI | 分佣、结算、提现、打款门禁 | **深度领先** ●●●●● |

**差距说明**：不要用「功能清单长度」衡量。通用平台赢在广度；你们赢在「会长申请→分佣→结算→提现」这条链的可执行语义。

### 3.2 用例 / 资产 / 目录

| 对比项 | 市面 | 我们 | 评分 |
|--------|------|------|------|
| 用例库 / 版本 / 标签 | 标配 | 无独立用例库；Pipeline JSON + 步骤定义 | ●○○○○ |
| 需求 / 用例追溯 | 常见（Jira 字段树） | 文档链到 md / 抓包说明 | ●●○○○ |
| 场景目录 | 文件夹 / Suite | 单条 money 主链为主；biz_flow / seed 分散 | ●●○○○ |
| 可视化编排编辑器 | 拖拽 / 录制 | 无（明确非目标） | — |
| wired/stub 诚实标记 | 少见 | **有**，防假绿 | ●●●●○ |

**主要差距**：资产中心化弱——Apifox 场景、PW 脚本、造数、主链步骤仍是「多入口」，面板尚未变成唯一资产目录。

### 3.3 编排与执行引擎

| 对比项 | 市面 | 我们 | 评分 |
|--------|------|------|------|
| 多引擎混编 | 多为「同框架 Suite」或 CI job 串联 | **单 Pipeline 内** SQL/SDK/回调/表单/PW | ●●●●○ |
| 并行 / 分片 | Grid、shard、云并发 | **单槽串行** | ●○○○○ |
| 队列与优先级 | 多级队列、资源池 | 单队列 FIFO | ●●○○○ |
| 条件分支 / 补洞 | 脚本 if；平台少业务分支 | S0 自动申请游戏等业务分支 | ●●●○○ |
| Profile / 档位 | env / tag | 档 A / B / 一键主链+打款开关 | ●●●○○ |
| 失败策略 | fail-fast / continue / retry | 遇 stub 停；失败停 | ●●●○○ |
| 定时日跑 | 标配 | PRD P2，未落地 | ●○○○○ |
| 分布式 Agent | Runner / Grid Node | 无 | ●○○○○ |

**主要差距**：规模化执行（并行、多机、定时、资源隔离）。  
**优势**：同一条业务链上的多协议编排，通用平台通常要自己拼 CI。

### 3.4 结果、断言与证据

| 对比项 | 市面 | 我们 | 评分 |
|--------|------|------|------|
| 步骤级结果 | 标配 | 有 | ●●●●○ |
| 期望/实际断言表 | Allure 风格常见 | 有（中文报告+抽屉） | ●●●○○ |
| 业务金额断言 | 需自写 | **内建分佣口径** | ●●●●● |
| 截图 | 标配 | PW 步骤已接（S7/10/11） | ●●●○○ |
| 录像 | 常见 | 无 | ●○○○○ |
| Playwright Trace | Currents/TestDino 内嵌；Allure 多为附件 | 无 | ●○○○○ |
| 网络/Console 时间线 | Trace Viewer 级 | 无 | ●○○○○ |
| 报告形态 | Allure/HTML/云端 Launch | 自研 HTML + 本地 log | ●●○○○ |
| 证据脱敏 | 程度不一 | Cookie/密码不展示明文（业务参数） | ●●●○○ |

**主要差距**：调试深度仍停在「截图+日志」，未到「可时光旅行的 Trace」。

## 5. 根因：不是「少写了功能」，是品类不同

| 市面平台默认假设 | 我们的假设 |
|------------------|------------|
| 测试对象是「软件产品」 | 测试对象是「分发/会长/充值分佣资金链路」 |
| 失败 = 断言/UI 挂了 | 失败还可能是「未申请游戏 / 签约 / 极验 / 打款开关」 |
| 执行器是同质浏览器网格 | 执行器是异构：SDK HTTP、ThinkPHP 表单、MySQL、PW 后台 |
| 价值在「覆盖率与稳定性」 | 价值在「这条钱能不能在测库跑通并留下业务 id」 |

因此：

- **抄 Allure 全功能** → ROI 低，且丢优势  
- **把业务链做成可插拔 Pipeline 模板 + 把证据/通知/追溯补到「够用」** → ROI 高

## 6. 建议优先级（缩小差距，但不改赛道）

### P0（1～2 周，性价比最高）

1. **失败聚合页**：按 `stepId + error 指纹` 统计近 7/30 日 Top 挂点（补「哪步总挂」）  
2. **通知**：跑失败/stub 停 → 企微/飞书 Webhook  
3. **证据包标准化**：每步统一 `log + assertions + screenshots[+ optional trace]` 目录约定  
4. **一键提单**：失败 run → 禅道/产品系统缺陷（你们已有技能，接到面板）  

### P1（与市面「像样」对齐的最小集）

5. Playwright **Trace on failure**（比继续堆截图更接近 Currents）  
6. **定时日跑**档 A + 可选主链（无人值守）  
7. **启动恢复 / 自动重试 ≤3**（PRD 已写，对齐 996）  
8. Apifox **variables 桥**（混编变量互通，避免双系统各说各话）  
9. Pipeline **目录扩到第 2～3 条业务链**（证明平台不是「单脚本壳」）  

### P2（可选，视团队是否要「像 TestOps」）

10. 简易用例/场景登记表（Apifox `-t`、planId、脚本路径）  
11. 本机轻鉴权 / 操作审计  
12. 报告占用清理、多 Worker（仍建议单业务机多进程，而非上 Grid）  

### 明确可不做（或外接）

- 自建 Selenium Grid / 云真机矩阵 → 用 BrowserStack 或现有设备农场  
- 完整手动用例 TMS → 继续用现有用例系统 / Apifox  
- 企业级 AQL 与多维 BI → 导出 JSON 给数据侧即可

## 7. 「追上先进平台」的误区清单

| 误区 | 后果 |
|------|------|
| 功能对标 Allure TestOps 打勾 | 半年后仍无第二条业务链，看板很空 |
| 先上多机并行再稳主链 | 假绿/假红放大，排查更难 |
| 用通用断言替代分佣 SQL 口径 | 业务验收失真 |
| 报告追求「好看」不追求「业务 id + 金额」 | 复盘时仍要人工翻库 |

## 9. 结语

市面「先进自动化平台」赢在：**资产、规模、协作、调试工业级深度**。  
你们赢在：**游戏分发资金链路的可执行知识**，以及「不假绿」的接线纪律。

下一阶段的正确问题不是「如何做成 Allure」，而是：

> **如何让每条业务主链在面板上像钱链路一样：可一键跑、可看业务参数、可留证据、失败可通知可提单——同时把 Trace / 热点 / 日跑补到「够工程化」。**

这样 80% 的日常测试指挥在面板完成，其余 20% 的通用能力继续外包给 Apifox / CI / 现有缺陷系统。
