# 测试用例八要素

写一条合格用例，至少把下面 **八项** 写全、写清。  
（注意：这和「测试八大要素 / 原则」不是一回事——原则管怎么测，八要素管用例怎么写。原则见 `03-测试八大要素.md`。）

## 总览

| # | 要素 | 一句话 |
|---|------|--------|
| 1 | 用例编号 | 唯一 ID，方便追溯、排期、提 bug |
| 2 | 用例标题 | 测什么 + 什么条件，扫一眼能懂 |
| 3 | 所属模块 | 挂在哪个项目/页面/功能下 |
| 4 | 优先级 | P0～P3（或高/中/低），决定先跑什么 |
| 5 | 前置条件 | 执行前必须满足的状态/数据/权限 |
| 6 | 测试步骤 | 可照做的操作序列 |
| 7 | 测试数据 | 本条要用的输入、账号、文件、参数 |
| 8 | 预期结果 | 可观察、可判定的正确表现 |

有的模板还会加：实际结果、执行人、执行日期、备注——那是**执行字段**，不是写作用例时的核心八要素。

---

## 1. 用例编号

- 建议：`模块缩写-功能-序号`，如 `PAY-RECHARGE-001`
- 同一套用例内唯一；改步骤可改内容，**尽量不改编号**（已关联 bug/报告时）
- 便于：需求追溯、自动化 ID、缺陷里写「复现用例」

## 2. 用例标题

- 格式倾向：`对象_条件_期望行为`  
  - 好：充值金额边界_0.01_可提交  
  - 差：测试充值、验证一下金额
- 标题里不要塞整段步骤；细节放步骤和数据里

## 3. 所属模块

- 写清：项目 / 端（Web·App）/ 一级模块 / 二级功能  
  - 例：商城后台 / Web / 订单 / 取消订单
- 方便按模块出报告、按模块回归

## 4. 优先级

| 级别 | 含义 | 典型 |
|------|------|------|
| P0 | 冒烟 / 主链路阻断 | 登录、下单支付、核心配置保存 |
| P1 | 主功能必测 | 主路径规则、主状态流转 |
| P2 | 次要功能 / 分支 | 少用入口、次要校验 |
| P3 | 体验 / 文案 / 弱网增强 | UI 微调、边缘兼容 |

一轮时间紧：先 P0 → P1，再按风险抽 P2。

## 5. 前置条件

写**执行前已经成立**的事，不要写成步骤：

- 环境：测试环境已部署 xx 版本  
- 账号：普通用户已登录 / 管理员已登录  
- 数据：存在一笔「待支付」订单 `ORDER_xxx`  
- 状态：购物车已有 1 件可售商品  

差：「打开登录页再登录」（那是步骤）。

## 6. 测试步骤

- 编号列出，一步一个动作；可复现即可  
- 避免「随便点点」「操作一下」  
- 涉及页面跳转时写清从哪到哪  

示例：

1. 进入「我的钱包 → 充值」  
2. 金额输入框录入「测试数据」中的金额  
3. 点击「确认充值」  
4. 在支付页完成支付（或 mock 成功回调）

## 7. 测试数据

- 与步骤分离：步骤写「做什么」，数据写「用什么值」  
- 含：输入值、账号密码（可用占位）、文件名、接口字段  
- 边界/等价类用例：数据栏写清代表值（如 `0`、`0.01`、`max+0.01`）

可写成表：

| 字段 | 值 |
|------|-----|
| 金额 | 0.01 |
| 支付方式 | 余额 |

## 8. 预期结果

必须**可判定**（看得到、对得上）：

- 界面：提示文案、按钮状态、列表多/少一条  
- 业务：订单状态 = 已支付；余额 +0.01  
- 接口：HTTP 200，`code=0`  
- 反例也要写：应失败时「无新订单、余额不变、有错误提示」

差：「成功」「正常」「没问题」。  
好：「Toast 显示“充值成功”；钱包余额增加 0.01；生成充值记录一条」。

## 完整示例（八要素齐全）

| 要素 | 内容 |
|------|------|
| 编号 | `PAY-RECHARGE-003` |
| 标题 | 充值金额边界_最小值 0.01_可提交成功 |
| 模块 | 支付中心 / App / 钱包 / 充值 |
| 优先级 | P1 |
| 前置 | 测试环境；用户 A 已登录；钱包可充值；余额已知为 X |
| 步骤 | ① 打开充值页 ② 输入金额 0.01 ③ 确认并支付成功 |
| 数据 | 金额=`0.01`；支付方式=余额（或指定渠道） |
| 预期 | 支付成功页；余额变为 X+0.01；充值记录金额 0.01、状态成功 |

---

## 自检（写完扫一眼）

- [ ] 八项都有，没有「标题有了步骤空着」
- [ ] 编号唯一，模块能归类
- [ ] 前置 vs 步骤没写混
- [ ] 数据与步骤对应，换数据可衍生边界用例
- [ ] 预期能判过/不过，可直接当 bug 对照
