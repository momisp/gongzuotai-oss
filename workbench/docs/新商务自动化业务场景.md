### 1.3 发现的问题

1. **聚合流水线的场景名和脑图对不上。** `p_scene_full` 是按旧脑图起的名：S2「场景三 一级建二级」、S3「场景四 二级建三级」在新脑图里都属于场景二；S7「场景六 解绑」在新脑图里场景六是换绑；S9「场景十 换绑」在新脑图里已并入场景六。面板上看起来像「场景六已通过」，其实跑的是解绑。
2. **假绿。** `p_scene_full.scene()` 只要子步骤没有 FAIL 就判 PASS，子步骤 BLOCKED 也算通过。11-11 那次 10/10 PASS 里，PAGE 层全部 BLOCKED，S9 换绑整条 BLOCKED，面板仍然全绿。这和引擎自己「不给假绿」的原则冲突。
3. **PAGE 层全部没接。** `Runner.page()` 固定返回 BLOCKED，所有页面断言（列表可见、Tab 可见性、置灰、空态）都没跑。
4. **场景一只确认了基线。** S0 只读了一次开关（含下级=开、去重=关），没有切换四个组合做对比。
5. **V2 指标没钉。** `v1reg_v2_01～08`（八卡、目标、绩效、小组等）的 `jsonPath` 都是 `$.data.TODO`、`jsonPathConfirmed: false`。
6. **V2 新业务没有流水线。** 目标下发、小组、目标达成、预警列表筛选 / 忽略 / 批量忽略、换绑都没有。
7. **预警处理链缺造数。** 一级名下没有系统扫描产生的预警，`v1reg_alert_record_handle` 一直 BLOCKED。

## 四、AI 接入指南

> 给后续接手的 Agent：按这一节做，不要自己另起一套引擎或另建面板入口。

### 4.1 硬规则

1. **只扩展现有引擎。** 新业务写成 `v1_regression_biz.py` 里的 `p_*` 函数，注册进 `PIPELINES`，id 必须以 `v1reg_` 开头（面板只按这个前缀分派到本引擎；用别的前缀会被当成充值 → 提现结算链执行，非常危险）。
2. **写操作只走 `r.http()`。** 它在 `writeEnabled=false` 时只记报文不发送。不要用 `requests` 直接发写请求，也**不要直接写业务库**（`db_select` 只读）。
3. **可重放。** 每条流水线要么自建自删，要么改完恢复原值，要么先查再写（已存在就 SKIP）。参考 `p_alert_gap`（读当前值 → 改 → 读回 → 恢复 → 确认已恢复）。
4. **不给假绿。** 条件不满足就返回 BLOCKED 并写清原因；后置断言依赖本轮写操作时传 `post_write=True`，预演态记 DRYRUN 而不是 FAIL。
5. **不碰别人的真实数据。** 只操作复用链 10060 / 10062 / 10063 名下或本轮自建的数据；审核类操作前先用 DB 断言确认目标记录是本轮造出来的。
6. **密码和 token 不进文档和证据。** OA token 每次动态登录取。
7. **改面板数据文件前先备份。** `wire_v1_biz.py` 会自动备份 `auto_control_pipelines.json`；手工改时自己备份。按仓库规则，大改前先提一个 checkpoint 提交。

### 4.2 接入一条新流水线的步骤

```
进度：
- [ ] 1. 在互补版里找到对应 BS 场景，列出步骤和断言
- [ ] 2. 确认接口：Apifox「新新商务接口」→ 没有 body 就去 sw2 前端 chunk 找表单字段 → 只读 GET 实测
- [ ] 3. 接口写进 config.api（key → method/path）
- [ ] 4. 写 p_xxx(r) 函数，每个断言一个步骤，标题以 [API] / [DB] / [PAGE] / [PERM] / [CHECK] 开头
- [ ] 5. 注册进 PIPELINES；在 wire_v1_biz.py 的 META 里加 name / group / depends / role
- [ ] 6. 预演：python v1_regression_biz.py --pipeline v1reg_xxx --dry-run，看证据里每步状态
- [ ] 7. 接线：python tools/wire_v1_biz.py --activate
- [ ] 8. 单条实跑（writeEnabled=true）：python v1_regression_biz.py --pipeline v1reg_xxx --execute
- [ ] 9. 需要的话加进 p_scene_full 的对应 BS 场景，再跑一次接线
- [ ] 10. 在本文第二节表里把状态改成「已有」
```

命令都在 `workbench` 目录下执行。

### 4.5 已知坑（实跑踩过的）

| 坑 | 正确做法 |
|---|---|
| `GET /sw/business/list` 按名字过滤 | 用 `userName`；`keyword` 会被忽略，返回全量 |
| `GET /sw/promote/list` 按账号过滤 | 用 `keyword`；`account` 会被忽略，返回全量 |
| 渠道账号带下划线 | 被拒（`code=7`），只能中文 / 英文 / 数字，4–30 位 |
| 预警规则启停 `enabled` | 只接受 `1` / `0`，`true` / `false` 报错 |
| 免预警 | 只能加本人名下渠道；绑定无效时候选为空 |
| sw2 的 token 调 OA | 不通，OA 要单独 `/base/login` |
| 解绑后渠道 | 记录还在，l3 看不到，幂等检查要用超管视角 |
| 审核通过和驳回 | 一条绑定只能走一个分支 |
| 渠道创建 | 必须在审核通过之后，否则 `bindOptions` 为空 |
| 频繁登录 | 会触发 sw2「验证码错误」，所有角色都登不上。取 token 只用 `r.token(role)`（走缓存），不要在步骤里自己调 `/base/login` |
| 复用账号被禁用 | 返回「用户被禁止登录」，先只读查 `sw9.sys_users.enable`，不要擅自改回 |
| 开关对比取数 | 「去重=开」冷查询可能超过 15 秒，`api_call` 要显式传更大的 `timeout` |
| `/sw/workbench/overview` | 必须带 `sourceDbList`，否则返回「请选择所属平台」 |
