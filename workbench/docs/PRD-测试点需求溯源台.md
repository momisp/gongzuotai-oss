## 0. 什么是 PRD（给你一句话）

**PRD = Product Requirements Document（产品需求文档）**。

不是代码说明书，而是「为什么做、给谁用、做成什么样、先做哪几块、什么叫验收通过」的共识文档。  
评审通过后再排期开发；改需求先改 PRD，避免边做边漂。

| PRD 里通常写什么 | 不写什么 |
|------------------|----------|
| 目标、用户、场景、界面规则、成功标准、分期 | 具体函数名、数据库表结构（除非强约束） |
| 做什么 / 不做什么 | 完整技术选型长文 |
| 验收清单 | 逐像素视觉稿（可另附原型） |

---

## 1. 一句话定位

在「测试点生成」旁增加 **需求溯源台**：以 **原型界面（或真实界面）为主体**，把 **原型说明** 与 **AI 测试点** 摆在同一屏，并通过 **区块互高亮 + 核验标记**，让测试人员一眼看出：

> 这条用例来自哪段需求、对应原型哪一块；有没有漏测、有没有多测。

远期再挂 UI 图、任务、Bug、报告、环境，形成「前后需求 → 用例 → Bug」一致性视图；**本期只把开发阶段的「原型三栏」做扎实**。

---

## 2. 要解决什么问题

| 痛点 | 期望 |
|------|------|
| AI 出了一大篇测点，难对回原型 | 点/悬停任一端，另两端立刻高亮同一「需求块」 |
| 担心漏功能 / 多功能 | 原型可见块 vs 说明段落 vs 测点子树可对照；未核验块显眼 |
| 说明、界面、用例分三处翻 | 单页三栏，不跳走 |
| 「我核过了」无法留痕 | 测点可标记「已核验」，颜色区分，可筛选 |

**不做的事（本期边界）**

- 不替代禅道缺陷库；Bug 仅预留挂载位  
- 不自动保证 100% 语义对齐（允许人工校正锚点）  
- 不以真实线上界面为主（真实界面属后续阶段）  
- 不在本期做完整「任务 / 测试报告 / 环境」总览墙（见分期）

---

## 3. 目标用户与成功标准

| 角色 | 场景 | 成功标准 |
|------|------|----------|
| 测试工程师 | 对照 AI 测点做人工核对 | 30 秒内找到「首页数据统计」对应的说明句与测点叶子 |
| 测试工程师 | 核验通过后留痕 | 点击测点 → 已核验（变色）；刷新后仍在 |
| 测试负责人 | 抽查覆盖 | 能列出「未核验」测点 / 「无测点锚点」的原型块 |

**量化（建议验收）**

1. 悬停三端任一目标，另两端对应高亮延迟 ≤ 100ms（本机）  
2. 单项目至少支持绑定 1 套前台原型（双原型时可选前台/后台切换）  
3. 核验状态按「项目 + 测点记录 id + 测点叶子 id」持久化，重开页面不丢失  

---

## 4. 产品原则

1. **一眼原则**：打开页面先看到「界面 + 说明 + 测点」，不先看菜单。  
2. **主体原则**：开发阶段 **原型图/原型交互页为主体**；说明与测点是旁注。  
3. **同源块原则**：高亮的最小单位叫 **需求块（Trace Block）**，三端共用同一个 `blockId`。  
4. **人工可改**：AI 可初建锚点，允许拖拽/点选校正；错锚可改，不可锁死。  
5. **核验是人活**：系统辅助定位，是否「测点写对了」由人点核验。

## 5. 概念模型（必须先统一）

### 5.1 需求块（Trace Block）

一条「可对齐」的最小需求单位，例如：

- 原型上的「平台数据统计区（2000+ / 500W+ / 4.9★）」  
- 说明里的对应段落  
- 测点脑图里的「显示平台总数据统计项」及子叶子  

| 字段（逻辑） | 说明 |
|--------------|------|
| `blockId` | 稳定 ID |
| `title` | 短名，如「平台总数据统计」 |
| `protoRect` | 原型上的矩形区域（相对截图或 iframe 坐标） |
| `descRange` | 说明文本起止（段落 id / 字符偏移） |
| `caseNodeIds` | 关联的测点节点 id 列表 |
| `source` | `ai` / `manual` / `mixed` |
| `verifiedCaseIds` | 已核验的测点叶子（可挂在核验表，不必塞进 block） |

### 5.2 三栏角色

| 栏 | 内容 | 交互 |
|----|------|------|
| 左 · 主体 | 原型预览（优先可交互 iframe；失败则截图） | 悬停/点击区域 → 高亮说明 + 测点 |
| 中 · 说明 | 从原型抓取的「原型说明」结构化段落 | 悬停段落 → 高亮原型区 + 测点 |
| 右 · 测点 | AI 已生成的框架/功能测点树（脑图或缩进树） | 悬停节点 → 高亮原型 + 说明；点击 → 核验切换 |

### 5.3 全链路信息架构（愿景地图，本期不全做）

一眼理解「整条开发链路」时，建议分层展示，避免一屏塞爆：

```
【主体层 · 当期必看】
  原型 / 真实界面  +  说明  +  测点（用例）

【旁路层 · Tab 或抽屉，按需展开】
  UI 图对照  |  研发任务  |  Bug  |  测试报告  |  测试环境  |  线上环境
```

本期只交付 **主体层 + 测点核验**；旁路层只占位（灰态入口），防止范围失控。

## 6. 核心交互（对应图一）

### 6.1 互高亮（Hover / Focus）

| 用户动作 | 系统反馈 |
|----------|----------|
| 鼠标移到原型某区域 | 该区域描边/遮罩高亮；中栏对应段落高亮；右栏对应测点节点高亮并滚动入视 |
| 鼠标移到说明某段落 | 左栏对应区域高亮；右栏对应测点高亮 |
| 鼠标移到测点某节点 | 左栏区域 + 中栏段落高亮；兄弟无关节点弱化 |

规则：

- 一对多允许：一块原型可对应多条测点；高亮全部关联叶子  
- 无锚点：悬停时提示「未关联」，并提供「建立关联」快捷入口（二期可做；一期可仅提示）  
- 离开悬停：取消高亮（若节点处于「选中/核验编辑」态则保持选中框）

### 6.2 核验（本期必做）

| 动作 | 行为 |
|------|------|
| 点击测点叶子 | 切换「未核验 ↔ 已核验」 |
| 已核验样式 | 另一颜色（建议：未核验默认；已核验青绿/蓝绿描边或底色） |
| 再次点击 | 取消核验 |
| 筛选 | 全部 / 仅未核验 / 仅已核验 |
| 进度 | 顶部展示「已核验 x / 可核验 y」 |

核验含义约定（写进 UI 小字）：

> 「已核验」= 人工确认：该测点与当前原型/说明匹配，表述可测、无多余臆造。  
> 不等于「测试执行通过」。

### 6.3 其它基础交互

- 左栏：缩放、适应宽度；双原型时切换「前台 / 后台」  
- 中栏：目录锚点、搜索段落  
- 右栏：展开/折叠；与现有「功能 / 框架」测点数据源切换（默认用「页面功能」叶子，可勾选含框架）  
- 一键「只看未关联测点 / 只看未覆盖原型块」（一期可做简化版：未关联测点列表）

## 7. 页面入口与信息流

### 7.1 入口建议

1. **测试点生成** 结果区新增 Tab：`溯源`（与 框架/场景/功能/专项/评审/PW 并列）  
2. 或底部按钮「打开需求溯源台」→ 全屏/宽屏工作区  

进入条件：

- 已有当前项目上下文  
- 至少有一份原型 URL（或本地 HTML）  
- 至少有一份已生成测点（框架或功能）；无测点时右栏空态引导去生成  

### 7.2 数据从哪来

| 数据 | 来源 |
|------|------|
| 原型主体 | 素材 URL / 双原型；**多页图册截图**（每路由一帧）+ 新标签可点 |
| 原型说明 | **点击浮钮「原型说明」** 抽取的侧栏全文（界面作用 / 字段与功能）；更新记录另段 |
| 测点树 | 当前工作区 framework / 功能 Markdown |
| 锚点 | **生成时 Trace Pack**（关键字 DOM + LLM 挂 caseIds）为主；无 Pack 时降级文案粗对齐；可人工改 |
| 核验态 | 本地 `verifyMap`（projectId + recordId） |

## 8. 分期建议（控制大版本风险）

### 一期（MVP · 已落地）— 三栏 + 互高亮 + 核验 + 截图兜底 + 导出

| 必做 | 说明 |
|------|------|
| 三栏布局 | 左原型 · 中说明 · 右测点 |
| 互高亮 | Hover 任一侧，另两侧同块高亮（文案粗对齐） |
| 测点核验 | 点击叶子切换已核验；变色 + 进度 + 筛选 |
| 截图主体 | xm 等禁 iframe 时用服务端 Playwright 截图；「新标签打开原型」 |
| 核验导出 | Markdown 核验报告 |
| 入口 | 测试点生成 Tab「溯源」+ 另起窗口 |

### 一期补强（2026-09-22 实测后确认）— 说明面板 + AI 锚定 + 多页图册

宇宙直播实测结论：单张截图 + 事后 Jaccard **不够**；应按下面三条补强。

#### 8.1 中栏说明 = 原型浮钮「原型说明」全文（图一）

| 点 | 做法 |
|----|------|
| 来源 | Playwright **点击「原型说明」** 打开侧栏，抽取「界面作用 / 字段与功能」条目 |
| 并存 | 「更新记录」仍单独抽取，并入需求变更，**不**当被测模块 |
| 切段 | 按「字段名：…交互：…」列表项切成段落，供悬停高亮 |

#### 8.2 精确框 UI：优先「生成时 Trace Pack」，不是事后扫热区

**结论：可以、也应该让 AI 介入；最佳时机是测试点生成过程，而不是溯源时再猜。**

推荐流水线（图二效果：关键字 ↔ 控件框）：

```
抓取页
  → 打开「原型说明」抽条目
  → 从条目抽关键字（【立即入驻】「成为主播」/ 段首「入驻引导区」）
  → 在 DOM 上按文案定位 getBoundingClientRect（确定性，便宜）
  → 关掉面板，截干净页图
  → 生成框架/功能测点时，模型输出带 blockId 的关联（说明条 → 测点叶子）
  → 落盘 Trace Pack，溯源台只读 Pack 做三栏高亮
```

| 锚定方式 | 何时用 | 精度 |
|----------|--------|------|
| **A. 说明关键字 → DOM 矩形** | 抓取阶段自动 | 高（图二同款） |
| **B. 生成时 LLM 输出 Trace Pack JSON** | ①框架 / ③功能生成 | 中高（负责测点挂接） |
| **C. 视觉框选（多模态）** | 仅对 A/B 失败的孤儿块 | 中（贵，慎用） |
| **D. 人工拖拽校正** | 演示前精修 | 最高 |

**Trace Pack（随测点记录持久化）建议字段：**

```json
{
  "pages": [{ "pageId": "home", "title": "首页", "shotUrl": "...", "hash": "#/" }],
  "blocks": [{
    "blockId": "b_入驻引导",
    "pageId": "home",
    "title": "入驻引导区",
    "descText": "入驻引导区：文案 + [立即入驻，成为主播]…",
    "keywords": ["立即入驻", "成为主播"],
    "protoRect": { "x": 0, "y": 0, "w": 0, "h": 0 },
    "caseIds": ["c_xxx"],
    "source": "spec-keyword+llm"
  }]
}
```

溯源台：**禁止再依赖「仅 5 个导航热区 + Jaccard」作为主路径**；粗对齐仅作无 Pack 时的降级。

#### 8.3 左栏改「多页图册」（演示墙）

| 点 | 做法 |
|----|------|
| 抓取 | 顶栏/侧栏导航每进一页留一张干净截图 + 该页说明条目 |
| UI | 左栏页签 / 缩略图切换（首页 · 热门直播 · 公会合作 · …） |
| 测点 | 叶子挂 `pageId`；悬停时先切到对应页再画框 |

**补强验收（宇宙直播）**：中栏有字段条目；左栏 ≥2 页图册可切换；Pack.blocks 含 `protoRect`；悬停可切页高亮。

### 二期 — 锚点精修与人工校正

- Trace Pack 可视化编辑（拖拽改框、改关联）  
- 未覆盖 / 孤儿测点报告强化  
- 可选：对孤儿块跑一次多模态补框  

### 三期 — 旁路层挂载

- Bug / UI 图 / 环境 / 任务（同前）  

### 四期 — 真实界面为主体

- 测试/上线阶段切换主体为真实页（同前）

## 11. 风险与开放问题（评审时拍板）

1. **坐标基准**：热区相对「整页截图」还是「可视 iframe」？SPA 滚动后如何重算？  
2. **说明切分**：按标题 / 按列表项 / 按 AI 语义段？错切会直接影响高亮体验。  
3. **测点粒度**：核验到「叶子」还是「### 小节」？建议叶子。  
4. **多对多**：一块对多测点时，悬停测点 A 是否弱化同块其它测点？建议弱化。  
5. **权限**：仅本机个人数据即可，还是要导出核验报告给同事？
