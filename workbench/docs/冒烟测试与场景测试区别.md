# 冒烟测试 vs 场景测试（业务测试）

> 面向日常排期与测试点编写：讲清两者分工，避免把「能登录」和「整条业务链路」混成同一种测法。

---

## 一句话区别


|          | 冒烟测试（Smoke）         | 场景测试 / 业务测试（Scenario）  |
| -------- | ------------------- | ---------------------- |
| **核心问题** | 这版还能不能用？主链路有没有当场断掉？ | 这条业务在真实条件下能不能跑通、结果对不对？ |
| **目的**   | **快速验活**、拦截致命缺陷     | **验业务正确性与分支覆盖**        |
| **深度**   | 浅：通 / 不通            | 深：条件 × 路径 × 结果         |
| **时机**   | 提测当日、每日构建、发版前闸门     | 功能测试中后期、需求验收、回归重点      |


---

## 1. 冒烟测试（Smoke Test）

### 1.1 定义

冒烟测试是对**新构建 / 新提测包**做的**最短、最关键**的可用性检查。  
名字来自硬件：「通电冒烟就别往下测了」——软件里同理：主入口都进不去，就不必开完整功能测试。

### 1.2 测什么

- 能否安装 / 打开 / 进入主界面  
- 核心账号能否登录  
- 最关键的 1～3 条主路径是否「能走完」（如：首页 → 下单 → 支付页能打开）  
- 明显崩溃、白屏、接口全挂、权限全无

**不测（或极少测）：** 复杂规则矩阵、边界组合、异常文案细节、全量字段校验。

### 1.3 特点


| 维度   | 说明                        |
| ---- | ------------------------- |
| 范围   | 窄：只覆盖「产品立得住」的骨架           |
| 用例量  | 少（常见十几条内，视产品而定）           |
| 执行时长 | 短（分钟级～一小时内为宜）             |
| 失败含义 | **阻断**：冒烟不过 → 打回，不进大面积功能测 |
| 通过标准 | 主链路可走通，无 P0 级阻塞           |




### 1.4 典型写法（叶子要「通不通」）

```
## 登录
- 账号密码登录能进入首页

## 首页
- 首页能展示轮播与金刚区入口
- 点击「请分身」能进入请分身内页

## 下单（主路径）
- （已登录）从商品详情能走到确认订单并唤起支付
```

## 2. 场景测试 / 业务测试（Scenario / Business Test）



### 2.1 定义

场景测试（常称业务测试、业务场景测试）按**真实用户目标与业务规则**设计路径：  
在给定角色、数据、配置下，验证「做完这件事，业务结果是否符合预期」。

它回答的不是「系统有没有挂」，而是：

> 这个业务在 A/B 条件下，该不该成功？成功后账、状态、展示对不对？



### 2.2 测什么

- 完整用户旅程（注册 → 请分身 → 祈福 → 查看记录）  
- **业务状态分叉**：已请分身 / 未请分身；余额足够 / 不足；当日已签到 / 未签到  
- **规则交叉**：开关开闭 × 同号判定 × 多渠道是否入池等  
- 跨模块结果：前端操作 ↔ 后台订单状态 ↔ 库存 / 次数 / 积分变化  
- 关键逆向：支付失败、次数用尽、审核驳回后的业务结果



### 2.3 特点


| 维度   | 说明                           |
| ---- | ---------------------------- |
| 范围   | 按业务模块组织，可比冒烟宽得多              |
| 用例形态 | 场景 / 能力清单 + 条件结果叶子           |
| 执行时长 | 明显长于冒烟                       |
| 失败含义 | 多为**需求/实现缺陷**，不一定整包打回（视严重级别） |
| 通过标准 | 约定场景下业务结果正确、关键分支覆盖达标         |




### 2.4 典型写法（叶子要「条件 + 业务结果」）

```
## 请分身
- 未请分身时可免费请分身并获得编号
- 已请分身后不再走「请分身」主按钮流程

## 签到领福
- （当日未签到）签到成功，福缘次数 +N
- （当日已签到）不可重复签到领取

## 入池 · 同账号判定
- （手机号判定开启；同号渠道 B 不满足入池）渠道 B 不入池，同号渠道 A 也不入池
```

> 业务场景宜写「能不能通、结果是什么」；逐步点哪个按钮、弹窗文案，留给**页面功能测试**。

## 3. 对照总表


| 对比项     | 冒烟测试            | 场景 / 业务测试                    |
| ------- | --------------- | ---------------------------- |
| 别名      | Smoke、构建验证、提测门禁 | Scenario、业务场景、端到端业务验         |
| 目标      | 发现**阻塞性**问题     | 验证**业务正确性**与路径覆盖             |
| 设计依据    | 发布清单 / 主路径清单    | 需求、规则、用户旅程、状态机               |
| 数据要求    | 最少可用账号与配置       | 常需多套账号、开关、库存、订单态             |
| 与自动化    | 最适合做 CI 日构建门禁   | 适合稳定后的关键路径自动化 + 手工补规则        |
| 和功能测试关系 | 功能测试的**前置闸门**   | 功能测试中的**业务主线**；细节 UI 另归页面功能点 |
| 失败处置    | 通常直接打回开发        | 按缺陷分级排期修复                    |

## 4. 和「页面功能测试」的三角关系（本仓库习惯）

工作台测试点生成三步与本文概念对齐如下：

```
① 页面框架     → 结构地图（Tab + 入口挂载内页）
② 业务场景     → 双段输出：
                 · 冒烟门禁（≤15 条主链路，通不通）  ≈ 本文「冒烟测试」
                 · 业务场景（条件 × 业务结果）      ≈ 本文「场景/业务测试」
③ 页面功能     → 测行为少抄皮（≥70% 交互/校验/空态；标 [P0]/[P1]/[P2]）
                 禁止逐条抄商品价；禁止业务结果叶子（归②）
```


| 层级 | 关注点 | 例子 |
|------|--------|------|
| 冒烟门禁（② 第一段） | 主链路通不通 | 登录 → 首页 → 能进请分身 |
| 业务场景（② 第二段） | 业务对不对 | 已签到不能再领；同号判定开启后连带不入池 |
| 页面功能③ | 点了什么→界面变成什么 | `[P0] 点「取消」关弹窗且不提交`；空提交有提示文案 |


**常见误区：**

1. 把冒烟写成上百条细则 → 失去「快」的意义。
2. 把业务场景写成逐步 UI 剧本或只写功能名词 → 与功能测试重复 / 无法当用例。
3. 冒烟不过仍强行开业务大测 → 浪费人力，缺陷定位也乱。
4. 把吸顶、背景音乐等展示细节写进业务场景 → 应归页面功能。
5. 把功能点写成「每个商品一条价格」的文案对照表 → 维护成本高，应抽样展示 + 侧重交互校验。

## 5. 怎么选、怎么排期


| 情况           | 建议                        |
| ------------ | ------------------------- |
| 新包刚提测 / 每日构建 | 先跑**冒烟**；不过则打回            |
| 冒烟通过后        | 按模块跑**业务场景**（优先 P0 旅程与规则） |
| 场景通过后        | 补**页面功能**与边界、兼容           |
| 紧急热修只改一处     | 冒烟 + 相关 1～2 条业务场景即可       |
| 大版本 / 新业务上线  | 冒烟门禁 + 完整业务场景 + 抽样功能点     |


**经验比例（仅参考）：**  
冒烟约占回归精力的 **10%～20%**；业务场景 **30%～50%**；其余给功能、边界、专项（性能/安全/兼容）。

## 6. 同项目示例（魁星岩小程序 · 示意）

**冒烟（最少集）：**

- 进入小程序首页不白屏  
- 暂不登录 / 微信登录能进首页  
- 请分身入口可进内页  
- 商城推荐卡片可进商品详情

**业务场景（在冒烟之上加条件与结果）：**

- 未请分身 → 请分身成功 → 获得编号  
- 已请分身 → 点香次数用尽 → 弹出补充次数  
- 当日未签到有「领福」角标；签到后角标消失且次数增加  
- 数藏已售罄卡片展示「已售罄」且不可完成购买

---



## 7. 结论

- **冒烟** = 门禁：快、浅、只问「还能不能测下去」。  
- **场景 / 业务测试** = 验业务：按真实目标与规则，问「这条业务做对了没有」。  
- 两者互补：冒烟不过不开大测；业务场景通过不代表 UI 细节都过——细节仍靠页面功能测试补齐。

编写测试点时：冒烟保持短主链路；业务场景写清**条件 + 业务结果**；不要互相抢活。
