## 给接手 AI 的约束（先读）

1. **一次只做一条**，做完自测再做下一条；每条做完提一个小提交（仓库规则：大改前先 `chore: checkpoint ...`）。
2. **不要重写面板**。`auto_control.js` / `auto_control.py` 很大，只做定点修改；改前用 Grep 找到行号再 Read 局部。
3. **不要动资金链路**（`_run_profile_a/_run_profile_b`、`money_flow`、充值→提现）的业务逻辑，除非条目明确要求。
4. **不要在 sw2 上频繁登录**：会触发验证码，锁约 1 小时。自测新商务时优先用 `--dry-run`，并且只跑单条。
5. 密码、token 不写进文档、日志、提交；`data/v1_regression_biz_config.json` 不入库。
6. 每条的「验收」是判断做完的唯一标准；做不到就在本文档对应条目下写「卡在哪」，不要硬凑。

优先级：**P0** 影响判断对错或有误操作风险；**P1** 明显提升定位效率；**P2** 体验和长期维护。

## 一、测试人员使用角度

### U1【P0】总览页仍写死「资金链路 / 十场景」

- 现状：`auto_control.html` 第 16 行标题标签「资金链路」；第 63、72、75、81 行写死「新商务 v1 全量回归 · 十场景聚合」「场景一/九」。流水线已改名为「新商务全量回归 · BS 场景聚合」，场景改成 BS 编号。
- 改法：标题标签改为「多业务」或去掉；场景卡标题从 `/api/auto-control/pipelines` 里取 `v1reg_scene_full.name`；说明文字改为「数据验证类场景（BS-01、BS-16）…」。
- 验收：页面上看不到「十场景」「场景一/九」字样；改流水线 name 后刷新页面标题跟着变。

### U2【P0】场景卡的状态显示和标题截断失效

- 现状：`auto_control.js` `renderSceneCard()`（约 314 行）用正则 `^(场景[一二…十]+)` 截短标题，BS 编号不匹配，标题会整段显示；状态直接显示英文 `passed/failed/skipped`；`skipped` 一律黄色，分不清「被阻断」和「本来就不判」。
- 改法：
  - 标题截取改为匹配 `^(BS-\d+(?:\/\d+)*)`，取不到就显示全称前 16 字。
  - 状态用 `zhMap(ZH.status, …)` 转中文。
  - 从 step.detail 里读出 `[BLOCKED]` / `[SKIP]` / `[DRYRUN]` 前缀（引擎回写格式见 `v1_regression_biz._sync_panel_steps`），分别显示「阻断」「不判定」「预演」。
- 验收：场景卡每行形如「BS-04 · 阻断」，颜色区分通过 / 失败 / 阻断 / 不判定。

### U3【P0】页面上有两个 `id="ac-stop"`

- 现状：`auto_control.html` 第 37 行（顶栏）和第 64 行（总览）都是 `id="ac-stop"`，`$("ac-stop")` 只能绑到第一个，总览里的「停止」按钮可能点了没反应。
- 改法：总览那个改为 `id="ac-stop-ov"`，在 `bind()` 里两个都绑到 `stopRun`。
- 验收：两个停止按钮都能停掉正在运行的任务。

### U4【P0】运行详情里的资金链路提示串到新商务

- 现状：`openDrawer()`（约 1250 行）只要 `s.id === "S4"` 就显示「玩家段按接口实调：注册、登录、实名…」。新商务聚合流水线也有 S4（BS-04 绑定审核），会显示这段无关提示。
- 改法：条件加上 `!String(run.pipelineId||"").startsWith("v1reg_")`，或者改为只对资金链路流水线 id 生效。
- 验收：打开一次 `v1reg_scene_full` 的运行详情，S4 下没有这段文字。

### U5【P1】顶栏「平台」「一键跑主链」只对资金链路有意义

- 现状：顶栏「平台（龙翔/游趣/汇玩）」和「一键跑主链」是资金链路专用，新商务流水线不看 `target`，但任务列表里仍显示「平台：龙翔」。
- 改法：任务列表和详情里，`v1reg_*` 的平台列显示「—（三平台）」；顶栏「一键跑主链」按钮 title 写明「资金链路」。不要删按钮。
- 验收：新商务的任务行平台列不再显示「龙翔」。

### U6【P1】任务列表状态筛选缺「未接线停止」

- 现状：`auto_control.html` 第 93～99 行筛选只有 排队/执行中/成功/失败/已取消。BLOCKED 的新商务 run 现在会落到 `status=failed, stopReason=stub_stop`，和真失败混在一起。
- 改法：筛选加一项「未接线 / 环境阻断」（前端传 `stopReason=stub_stop`，`list_runs` 支持该过滤）；任务行状态标签对 `stub_stop` 显示「阻断」灰色，不显示红色「失败」。
- 验收：筛「失败」只剩真失败；筛「阻断」能看到 BLOCKED 的 run。

### U7【P1】运行前没有环境预检

- 现状：`health()`（`auto_control.py` 约 2928 行）只检查 3780 回调和 Apifox token，跟新商务无关。今天实际踩到的三个问题都是跑完才发现：复用账号被禁用、sw2 登录要验证码、写闸门状态不明。
- 改法：给新商务加一个只读预检函数（放在 `v1_regression_biz.py`，如 `preflight(cfg) -> list[str]`），在 `health()` 里调用并把结果并入 `alerts`：
  - `writeEnabled` 当前值（开时提示「会真实写业务数据」）
  - `/base/captcha` 返回 `openCaptcha=true` → 提示「登录需验证码，自动化会全部阻断」（这个接口不算登录，不会加重锁定）
  - 只读查 `sw9.sys_users` 里 `config.reuse` 三个账号的 `enable`，为 0 就提示
  - **不要在预检里调用 `/base/login`**
- 验收：在验证码锁定或账号禁用时打开面板，顶部告警条直接说明原因。

### U8【P2】「跑一次全量回归」缺二次确认

- 现状：`enqueueSceneFull()` 直接入队；写闸门开时会真实写业务数据（绑定、审核、建渠道、改设置再恢复）。
- 改法：`writeEnabled=true` 时弹 confirm，文案列出会写的对象（来自预检）。
- 验收：写闸门开时点击会先确认；关时不弹。

## 二、后续新业务场景接入角度

### N1【P0】执行分派写死在 `_execute_run`

- 现状：`auto_control.py` `_execute_run()`（约 1286 行）按 `pipe_id == "oa_inner_tab_keep_filter"`、`== "guild_seed_ready"`、`startswith("v1reg_")` 分派，**其余全部落到 `profile A/B` 资金链路**。新业务如果 id 起错前缀，会被当成充值→提现执行，有误操作风险。流水线 JSON 里其实已有 `"runner": "v1_regression_biz.run_pipeline"` 字段，但没被用上。
- 改法：
  1. 在现有分支之前加：流水线定义里有 `runner`（形如 `模块名.函数名`）就 `importlib` 导入并调用 `fn(run_id, pipe_id, opts) -> (ok, err)`。
  2. 白名单：只允许 `workbench/` 下的模块（防止任意导入）。
  3. 兜底：没有 `runner` 且不属于资金链路已知 id 时，**报错「未配置 runner」而不是跑 profile A**。资金链路已知 id 从 `data/auto_control_pipelines.json` 里现有非 v1reg 的条目整理成常量。
  4. 保留原有 `v1reg_` 分支作兼容。
- 验收：新增一条带 `runner` 的测试流水线能被正确分派；删掉 `runner` 的未知流水线点跑时报「未配置 runner」，不会进入充值链。

### N2【P1】接线器只服务新商务一套

- 现状：`tools/wire_v1_biz.py` 的 `META` 和 `biz.run` 绑死新商务；以后接别的项目（OA、蜂巢等）要复制一份。
- 改法（KISS）：不要做通用框架。只把 `build_step()` / `_apis_from_evidence()` 抽到 `tools/wire_common.py`，新项目各写一个 `wire_xxx.py`，`import` 公共部分。
- 验收：`wire_v1_biz.py --activate` 输出与改前一致（同一份 `auto_control_pipelines.json` diff 只有时间戳类字段）。

### N3【P1】流水线定义里缺「业务场景来源」

- 现状：流水线只有 `group / role / depends / note`，看不出对应哪份测点、哪个 BS 场景。
- 改法：`META` 增加可选字段 `sceneRef`（如 `"BS-04"`）和 `sceneDoc`（测点文档路径），接线器原样写进 JSON；流水线详情弹窗（`openPipeModal`，约 700 行）显示这两项。
- 验收：流水线详情里能看到「场景：BS-04 · 业务场景-互补版-20261112.md」。

### N4【P2】流水线分组和项目归属靠 id 前缀猜

- 现状：`projLabel()`（约 306 行）按前缀猜项目（`v1reg`→新商务、`money|coin|guild`→充值提现）。
- 改法：流水线 JSON 加 `project` 字段（接线器写入），`projLabel` 优先读字段，读不到再按前缀。
- 验收：新项目流水线只要写了 `project` 就能在列表正确归类。

### N5【P2】新业务接入缺一张「最小清单」

- 改法：在 `新商务自动化业务场景.md` §4.2 之后加一句链接到本文 N1/N3，说明新项目必须填 `runner`、`project`、`sceneRef`。只改文档。

## 三、执行后定位问题角度

### D1【P0】新商务的步骤证据在面板里看不到

- 现状：新商务引擎把每步完整证据（请求报文、SQL、返回摘要、子步骤）写在 `data/v1_regression_biz_evidence/<流水线>_<时间>.json`，但面板 run 记录只回写了一行 `detail` 字符串（`_sync_panel_steps`）。运行详情里看不到报文和 SQL；聚合流水线的子步骤也被压成一行。证据文件和面板 run 之间没有关联。
- 改法：
  1. `v1_regression_biz.run()` 返回证据文件路径；`run_pipeline()` 把路径写进面板 run（如 `run["evidenceFile"]`，用 `auto_control._update_run`）。
  2. `_sync_panel_steps()` 额外回写每步 `apis`（复用 `wire_v1_biz._apis_from_evidence` 的逻辑）和聚合步骤的 `subSteps`（`evidence.sub_steps`）。
  3. 前端 `openDrawer()`：有 `subSteps` 时在该步骤下渲染一张小表（子步骤标题 / 状态 / 说明），默认只展开非 PASS 的行；`apisHtml(s)` 已能渲染 `apis`，直接复用。
  4. 详情里加「下载证据 JSON」链接（新增一个只读路由，只允许读 `data/v1_regression_biz_evidence/` 下文件）。
- 验收：打开一次 `v1reg_scene_full` 的运行详情，能展开看到 BS-04 下每个子步骤的状态、请求路径和 SQL；能下载对应证据文件。

### D2【P0】BLOCKED / DRYRUN / SKIP 在面板里都显示成「跳过」

- 现状：`_sync_panel_steps()` 把 BLOCKED、DRYRUN、SKIP 都映射为面板 `skipped`，只能靠 detail 前缀区分。
- 改法：面板 step 增加字段 `engineState`（原样写 PASS/FAIL/BLOCKED/DRYRUN/SKIP）；前端 `renderSteps` / `openDrawer` / 场景卡优先用它决定文案和颜色。`status` 字段保持原值不动，避免影响统计和资金链路。
- 验收：同一 run 里能一眼分出「阻断」「预演」「不判定」。

### D3【P1】失败原因没有分类

- 现状：错误是一串文本。今天的失败其实分四类，处理人不同：产品缺陷（断言不符）、环境问题（账号禁用、验证码、超时）、数据前置不满足（没有预警记录、没有待审核记录）、自动化本身问题（参数名错、未接线）。
- 改法：引擎层 `Runner.step` 已能识别「禁止登录」「验证码」；扩成一个小函数 `classify(detail) -> "product" | "env" | "data" | "automation"`，规则用关键词表（放常量，方便加）。结果写进证据和面板 step（`failClass`）。前端失败行显示一个小标签；失败热点 `compute_hotspots()` 按分类分组。
- 验收：人为造一个验证码失败，详情和热点里显示「环境」。

### D4【P1】一键提缺陷没过滤环境类失败

- 现状：`build_ticket_draft()` / `create_ticket()`（约 3809 行）对所有 failed/cancelled 开放。环境类失败（D3）提成产品缺陷会污染缺陷库。
- 改法：`failClass` 为 `env` / `automation` 时前端禁用提缺陷按钮，title 写原因；后端 `create_ticket` 也做同样拦截（返回明确错误）。
- 验收：环境类失败无法提缺陷，产品类失败正常。

### D5【P1】和上次结果没有对比

- 现状：看一次 run 只能看这一次，不知道「这条是新坏的还是一直坏」。
- 改法：运行详情顶部加一行「与上一次同流水线运行对比」：列出状态从 PASS 变成 FAIL/BLOCKED 的步骤（按 step id + 标题匹配）。后端在 `get_run` 返回里附带 `prevRunId` 和 `diff`（只比 step 状态，不比报文）。
- 验收：连续跑两次，第二次某步变坏时详情顶部能看到「新坏：S4 BS-04 …」。

### D6【P2】证据和备份文件只增不减

- 现状：`cleanup_runs()` 只清运行目录；`data/v1_regression_biz_evidence/` 已有数百个文件；`data/auto_control_pipelines.json.bak.*` 每次接线都新增一份。
- 改法：`cleanup_runs()` 同时清理这两处，规则同运行记录（保留 14 天，且每条流水线至少保留最近 5 份证据；备份只留最近 10 份）。
- 验收：设置页「报告清理」执行后，两处文件数下降且最近的保留。

### D7【P2】运行日志没有记录新商务引擎的关键信息

- 现状：新商务 run 的日志只有「开始执行」「失败: …」。
- 改法：`run_pipeline()` 结束时写一行汇总到面板日志（`auto_control._write_run_log`）：`writeEnabled`、各状态计数、证据文件名、耗时最长的 3 步。
- 验收：日志尾部能看到这行汇总。
