### 0.3 架构判断：总后台 / 会长端 = **未前后端分离**

你的判断对。对照抓包，总后台与会长端是典型 **ThinkPHP / CMF + Simpleboot 服务端渲染**，不是 Vue/React + `/api/v1` 那套。

| 特征 | 抓包里的表现 | 和「真 REST」的差别 |
|------|--------------|-------------------|
| URL | 一律 `*.html`（如 `dologin.html`、`generatesettlementall.html`、`do_confirm.html`） | 不是 `/api/...` 资源路径 |
| 鉴权 | `PHPSESSID` + `admin_username` / `__LOGIN_BY_CMF_ADMIN_PW__` Cookie | 无 Bearer Token；会话绑浏览器 |
| 列表/菜单页 | `Accept: text/html`，整页 HTML（带筛选 query） | **没有**独立「列表 JSON API」可指望 |
| 操作提交 | `application/x-www-form-urlencoded` + 常带 `X-Requested-With: XMLHttpRequest` | 像「页内 AJAX」，响应可能是一小段 JSON **或** 直接跳转/HTML |
| 静态资源 | `lxcdn…/simpleboot3`、`layer.js`、`artDialog` | 传统后台皮肤，前后端同仓 |
| 页面 vs 提交 | 会长：**看页**走 `/tg/...`，**提交**走 `/channelsite/...` | 同一业务两套路径，仍是服务端 MVC |

**和玩家段对比**

| | 玩家 SDK | 总后台 / 会长 |
|--|----------|----------------|
| 形态 | JSON Body + `md5_sign`，适合 Apifox | Cookie + 表单 / 偶发 XHR |
| 取业务 id | 响应字段或 SQL | 列表多在 **HTML 表格**里；或直接 **查库** |
| 工作台已有封装 | `game_sdk_api.py` | `channel_web_api.py` / `biz_web_api.py`（同风格：`_post_form` + Cookie） |

**自动化怎么搞（建议口径，写入引擎列）**

1. **动作步**（结算、确认、提现、审核、打款）：继续用 HTTP 复现抓包——本质是「带 Cookie 的表单/伪接口」，文档里标 **`HTTP·表单`**，不要当成 OpenAPI。  
2. **取 id**（`periodId` / `withdrawId`）：优先 **SQL**（稳、不解析 HTML）；次选 GET 列表页后正则/BeautifulSoup 抠；或 Playwright 点选。  
3. **断言金额/状态**：优先 **库表**；页面只做冒烟可见性。  
4. **整段不会抓包时**：Playwright 点页面也可（和表单 HTTP 二选一即可，符合你「先搞一套走流程」）。  
5. **会话**：总后台 Cookie ≠ 会长 Cookie；会长抓包里若仍带 `admin_username`，说明同浏览器串了，脚本要拆开登录。

> 下文表格里原写「API」的总后台/会长步骤，均按 **HTTP·表单（非前后端分离）** 理解；只有玩家 SDK 才是严格意义的接口自动化。

## 5. 推荐编排（怎么串成一条可跑场景）

### 5.0 先定调：整段不是「全接口自动化」——要怎么搞

结论：**九步闭合是「混合自动化」**，不要按 Apifox 一条龙硬套。能接口的接口，不能的用「Cookie 表单 HTTP / SQL 断言 / Playwright 点页」补齐，由工作台编排串起来。

```text
┌──────────────┬─────────────────────────────┬──────────────────────┐
│ 区段           │ 实际形态                      │ 推荐自动化方式         │
├──────────────┼─────────────────────────────┼──────────────────────┤
│ 1～3 造数      │ OA 接口 + 商务/会长表单站       │ 已有 F1～F5；或种子跳过 │
│ 4～5 注册充值   │ 游戏 SDK（真 JSON 接口）       │ Apifox / game_sdk_api │
│ 回调+分佣断言   │ 本地模拟回调 + SQL             │ money_flow F9～F10    │
│ 6～9 结算提现   │ 总后台/会长 .html + Cookie    │ 表单 HTTP 复现抓包     │
│              │ 列表多为 HTML                 │ id/金额：优先 SQL      │
│ 页面冒烟抽查   │ 同一套传统页                   │ Playwright（可选薄层） │
│ ③ 流水核验     │ 财务新页（开发中）             │ **暂不接入自动化**     │
└──────────────┴─────────────────────────────┴──────────────────────┘
```

**三种落地档（按投入选，不要混称「全接口」）**

| 档 | 名称 | 覆盖 | 怎么实现 | 何时用 |
|----|------|------|----------|--------|
| **A** | 钱链路日跑（已有） | 注册→模拟充值→分佣 SQL | `money_flow` / F8～F10 | **每天必跑**；资金回归底线 |
| **B** | 混合闭合（推荐目标） | A + 结算→确认→提现→审→打款 | 工作台 Python：`requests` 会话复现抓包表单 + SQL 取 id/断言；登录复用 `channel_web_api` / 总后台 dologin | 测环境打通后周跑/发版前 |
| **C** | 浏览器主路径 | 同 B，但 6～9 用 Playwright 点菜单 | 录/写 spec，断言仍可 SQL | 表单参数易变、或要留截图证据时 |

**B 档推荐骨架（脚本一层，不是 Apifox  alone）**

```text
money_flow_v1()                          # SDK + 回调 + 分佣
  → sql: settlementRowId
admin_login() → session_admin            # POST dologin.html，存 Cookie
  → GET generatesettlementall.html
guild_login() → session_guild            # channel_web_api 已有
  → sql/html: periodId
  → POST channelsite/.../do_confirm.html
  → sql: balance_profit ↑
  → POST .../withdrawal.html
  → sql: withdrawId
  → session_admin: changestatus → paid
  → sql: 提现单终态 = 已打款
```

可选：关键页 Playwright 截一张「已打款」作证据，**不替代** SQL 断言。

**明确不要做的**

- 不要对外说「整条已是接口自动化」——总后台/会长段不是。  
- 不要为列表硬找 REST；**id 查库**比解析 HTML 稳。  
- 不要把极验/短信塞进无人值守主链（测环境关验证或半自动填一次 Cookie）。  
- 不要日跑打真实微信打款；打款步设开关，默认测环境手工确认过的 `choose_type`。

**和脑图「先搞一套」对齐**：先落 **A 日跑 + B 混合闭合一条脚本**；C 只补不好表单化的页。部分功能「两个地方都能做」时，**动作用表单 HTTP，核对用 SQL**，页面作备选。
