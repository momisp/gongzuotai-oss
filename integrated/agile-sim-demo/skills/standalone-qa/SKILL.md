## 语言要求（强制 · 简洁且准确）
- **简洁**：一句一个可验证点；删掉「验证一下」「检查是否」「相关逻辑」等空话；少用长定语从句。
- **准确**：条件、开关开闭、对象（渠道/账号/字段）、期望结果必须写死，不能含糊替代。
  - ✅ `（手机号判定关闭）两渠道同手机号，渠道 A 满足入池条件 → 渠道 A 入池`
  - ❌ `验证关闭同账号判定后各渠道独立入池`（太笼统，仍需二次分解）
- **可直接当用例**：叶子节点读完就能配数据开测，**禁止**还要读者再拆一层的「汇总句 / 原则句」。
- 宁可多几条短叶子，也不要用一条概括句盖住整棵分支树。
- **用语口语化（禁止技术英文 / 图标字符）**：测试点是给人看的，不是源码注释。
  - ❌ `Toast「验证码已发送」` / `maxlength 6` / `placeholder` / `loading` 等 HTML/前端术语
  - ✅ `提示「验证码已发送」` / `最多可输入 6 位` / `占位符「请输入验证码」` / `显示加载中`
  - ❌ 把 `✎` `✓` `×` 等图标字符写进句子（如「ces 行 ✎」）
  - ✅ 写成「点击 ces 行的编辑按钮」/「展示已勾选」；**原型界面上本来就显示的英文文案或账号名**（如小号名 `ces`、按钮 `OK`）可以保留
  - **例外**：叶子优先级 `[P0]` / `[P1]` / `[P2]` 为规范强制，不算「技术英文」
  - 弹窗与弹窗内细则必须用**缩进嵌套列表**（父级 `- 安全验证弹窗`，子级再缩进 `- 标题…`），禁止把弹窗名和内部条目写成同级并排。

## HTML 原型特殊约定（重要）
许多 HTML 原型带有「原型说明」「更新记录」浮层/弹窗，里面是**给测试看的说明文档**（后者记录 PM 后续追加的需求变更），**不是被测产品功能**。
- 框架中禁止把「原型说明」「更新记录」列为页面/模块；禁止写打开/关闭它们的用例。
- 必须精读「原型说明」「更新记录」正文理解业务与迭代差异，再映射到真实页面。
- 同站多页合并进同一套框架，按用户旅程组织。

### 多原型·独立 vs 前后台双原型（强制）
- 素材标 **【双原型】**（前台/后台）：按 C 端 + 管理端组织，业务场景要写跨端闭环。
- 素材标 **【多原型·独立】**（如「新商务 v2」+「OA 某一页」）：两套系统各自成章，**禁止**写成前台/后台，**禁止**硬写跨端闭环。
- 排期里两个链接≠前后台；看素材标记与字段名（原型 A/B），不要凭「有两个 URL」就当双端。

### 本版范围 / 仅 V2（强制）
- 素材含 **【本版范围】** 或「仅生成 V2 / 按版本查看=V2」时：只覆盖该版本改动页与侧栏可见菜单（如商务绩效、小组、有效端、免预警、设置等）。
- 同一 HTML 包里仍有的 **V1 历史页**，若本版未改、侧栏在 V2 视图下已隐藏 → **不要**写成待测全量范围。
- 抓取正文若已注明 `biz_ver_view=v2`，框架与测点必须与之对齐。

### 三浮窗通读（强制 · 新商务等带版本原型）
右下角常有三个浮钮，抓取/生成前必须**全部通读**，缺任一段则框架易漏模块：
1. **改动汇总**（绿）：本版改了哪些页面、每页改点、全站项 → 框架一级模块须覆盖这些改动页
2. **原型说明**（蓝）：当前页字段/交互/口径 → ③功能点与筛选/列表以说明+可见界面为准
3. **更新记录**（橙）：PM 追加的规则变更 → 映射进场景/功能，不要写成「打开更新记录」用例
- 禁止把三浮窗本身列为被测入口；禁止只扫侧栏可见列表、忽略浮窗正文。
- **禁止「未展开」占位**：不得写「侧栏可见入口；本次抓取未展开页内区块」。预警规则 / 免预警渠道 / 设置 / 注册明细 / 区服分析 / 排行榜等改动页，须在入口下展开页内区块（筛选、列表、工具栏、弹窗）；抓取偏少时按改动汇总改点展开并标【待核实】。

### 可见入口 vs 隐藏弹窗（强制 · 防幻觉）
HTML 原型常把弹窗 DOM 整段写在页面底部（默认隐藏），「原型说明」里也会描述尚未接线的交互。
- **③ 功能测试点**：只写**当前页有明确入口**能点开的功能。入口 = 可见按钮/链接/行操作（如「流水」「查看」「搜索」）。
- 若某弹窗**仅出现在隐藏 DOM 或原型说明/更新记录**中，但页面**没有任何按钮/点击能打开它**（例如无「更换商务」「生成批次」按钮），则：
  - ❌ 禁止写「点击××弹出该弹窗」及弹窗内细则；
  - ✅ 可在框架业务简介中一句带过「说明中提及××（当前页未见入口）」；或业务场景里写需求意图，不写操作步骤。
- 以**肉眼能在默认界面看到的控件**为准，不以抓取到的隐藏 HTML 文案为准。

### 筛选区 vs 列表列（强制 · 严格按抓取原型）
- **搜索/筛选区**只挂抓取里搜索表单/筛选条**真实出现**的控件（输入框、下拉、日期、搜索/清空等）。
- **列表表头列**挂在「列表 / 列表区」下平铺；某字段若只出现在表头列、筛选条没有 → **禁止**写进筛选区。
- 例：抓取筛选仅有用户id/账号/简称/结算模式/账号状态/注册时间，而「认证状态」只在列表列 → 认证状态只挂列表，不挂筛选。
- 说明文案与抓取可见界面冲突时，**以抓取可见界面为准**；说明多写的筛选项可在简介注明「说明提及、界面未见」。

### 证据权威顺序（强制 · 说明缺步时防漏测/防臆造）
原型常出现「说明文案没写下一步，但可点演示已有结果」。仲裁顺序：
1. **关键按钮交互轨迹**（抓取里点入口/主按钮后的可观察变化：提示、关弹窗、回某页、编号切换）
2. **当前页/子页可见正文**
3. **原型说明 / 更新记录**正文

规则：
- 说明缺步、轨迹或可见正文已演示 → **按演示写**，可在叶子标 `【据原型演示】`
- 说明与演示冲突 → **以演示为准**，评审记「说明待补」
- 两边都没有 → 写 `【待核实】`，**禁止猜跳转目标页**
- 例：抢靓号成功弹窗点「立即使用」→ 回分身页 + 提示「靓号已生效」+ 编号切换；「进入我的靓号」只挂在「记录」入口，勿写到「立即使用」上

## 梳理顺序（强制 · Tab 顶层 + 入口挂载内页）

对齐手写 XMind：**先按主导航/Tab 分大块，再从入口把目标页整棵挂下去**；不要「所有页面互相平级」。

1. 一级 `##`：**仅** App 底部 Tab / 顶部主导航 / 后台左侧一级菜单（例：首页、祈福服务、文创商城、我的；或工作台、内容管理…）。
   - 有几个一级入口就几个 `##`，**不要**给每个二级页、弹窗、内页单独开 `##`。
2. 二级 `###`：该 Tab/模块**当前页**内的区块，按界面从上到下、从左到右（顶部导航、轮播、快捷入口、金刚区、列表、筛选…）。
3. `-` 叶子：区块内的入口、控件、角标说明；**能跳到另一页的入口**写成「入口名（进××页）」。
4. **入口挂载（强制）**：入口下方用缩进嵌套挂上**目标页整页框架**（页名 → 页内区块/态 → 控件/弹窗 → 若再跳转则继续挂）。
   - ✅ `快捷入口卡片` → `请分身（进…）` → `魁星岩·请分身` → `未请分身态` / `已请分身态` → …
   - ✅ `金刚区` → `签到领福（…）` → `签到领福` → `签到日历` → …
   - ❌ 把「请分身 / 还愿墙 / 签到领福 / 抢靓号…」全部提成与「首页」平级的一长列 `##`
5. 多入口进同一页：挂在**主入口**下即可；次要入口只保留「进××」指向，不必整树复制。
6. 全局页（授权登录、设置等）：挂在最自然的 Tab 下（如「我的 → 点击登录 → 授权登录」），不要单独冒顶成与 Tab 平级的一串 `##`（除非它本身就是一级导航）。
7. 每个一级 `##` 下仍要有一行 `> 业务简介：…`（该 Tab/模块一句话）；内页可用缩进列表表达，不必每个内页再开 `##`。

## 写作风格（强制 · 对齐手写 XMind）

### 总原则
- **短句、可验证、口语化专业**：一句一个点；少空话、无用例编号、无 JSON/Playwright。
- **句式模板**：`[（前置条件）]操作/状态，能/会/不会 + 可观察结果`
- **前置条件用括号写在句首**，与手写一致：`（有数据）` `（无数据）` `（已选择游戏）` `（未选择游戏）` `（余额足够）` `（余额不足）` `（有代理币余额）` `（无代理币余额）`
- **成对覆盖**：取消 vs 确定；有数据 vs 无数据；余额足够 vs 不足；正向路径 vs 逆向分支。
- **具体文案/数值必须落笔**：按钮文案加引号；默认值、枚举、金额写死数字。
  - ✅ `有文案「您确定要删除该游戏吗？」`
  - ✅ `下拉框默认勾选三个渠道（龙翔、汇玩、游趣）`
  - ✅ `能显示购买道具，后面有具体价格（如：价格：1000.00元）`
  - ❌ `有删除确认文案` / `默认勾选若干平台` / `显示价格`

### 业务规则必须拆到可测叶子（强制 · 禁止一概而过）
需求里若出现**开关组合、同号/同证绑定、多渠道各自是否满足条件、连带入池/不入池**等交叉规则，必须按维度拆成独立业务分支，每条叶子自带条件 + 结果。

**要拆的典型维度（有则必拆）：**
1. 配置开关：开 / 关（如「绑定手机号同账号判定」「身份证同账号判定」）
2. 共享关系：同手机号 / 同身份证 / 不同号
3. 各渠道自身条件：满足入池 / 不满足入池
4. 期望结果：该渠道入池 / 不入池（写到具体渠道，勿写「各渠道独立」了事）

❌ 禁止（仍需二次分解）：
```
## 入池规则
- 关闭手机号与身份证同账号判定后，跨平台账号不再捆绑，各自按条件入池
- 开启同账号判定时，一渠道不满足则同号渠道均不入池
```

✅ 正确（可直接当用例）：
```
## 入池 · 同账号判定
### 手机号判定关闭（各渠道同手机号）
- （渠道 A 满足入池条件）渠道 A 入池
- （渠道 B 不满足入池条件）渠道 B 不入池
### 手机号判定开启（各渠道同手机号）
- （渠道 B 不满足入池条件）渠道 B 不入池
- （渠道 A 满足入池条件）渠道 A 也不入池
### 身份证判定关闭（各渠道同身份证）
- （渠道 A 满足入池条件）渠道 A 入池
- （渠道 B 不满足入池条件）渠道 B 不入池
### 身份证判定开启（各渠道同身份证）
- （渠道 A 满足入池条件）渠道 A 不入池
- （渠道 B 不满足入池条件）渠道 B 不入池
### 手机号与身份证判定均开启
- （同手机号且存在一渠道不入池）同号各渠道均不入池
- （同身份证且存在一渠道不入池）同证各渠道均不入池
### 手机号与身份证判定均关闭
- （同手机号）各渠道仅按自身条件入池/不入池，互不影响
- （同身份证）各渠道仅按自身条件入池/不入池，互不影响
```

自检：若某条叶子还可以再问「开还是关？」「A 还是 B？」「入不入池？」，说明**还没拆够**，继续拆到不能再问为止。

### 功能测试点写法（③ · 测行为，少抄皮）

③ 写 **页面操作与界面反馈**，不是业务规则矩阵（归②），也不是静态文案对照表。

**比例（强制）**
- **≥70%** 叶子：交互 / 状态变化 / 校验失败 / 空态 / 成对按钮 / 开关与筛选结果  
- **≤30%** 叶子：静态展示（关键控件「能显示××」即可；**禁止**把推荐区每个商品的标题、划线价、限量份数逐条抄成叶子）  
- 同区块静态文案可合并为 1～2 条抽样，或写「推荐卡片能显示标题 / 价格 / 预约按钮（与原型一致）」

**与②分工（强制）**
- ❌ 禁止业务结果型叶子：福缘 −1、订单变为「待联系」、入池/不入池、连续签到发奖等 → 归②  
- ❌ 导航「点击入口进入 XX 页」：每个入口 **最多 1 条**；目标页内操作写在该页/该入口挂载章节  
- ✅ ③ 只写：点了什么 → 界面变成什么（含提示文案、选中态、弹窗开闭、列表刷新）

**优先级（强制 · 防 P0 膨胀）**
- 每个叶子前必须标 `[P0]` / `[P1]` / `[P2]`（禁止漏标）  
- **P0**：真正阻断主操作 / 主链路（打不开、提交无反馈、支付失败无提示、关键开关失效、空提交无任何阻断）  
- **P1**：常用交互、校验、筛选、成对取消/确定、空态  
- **P2**：次要展示、边缘文案、悬停、低风险样式、非阻断提示  
- **配额（强制自检）**：同一份③里，带 `[P0]` 的叶子 **≤ 全部已标叶子的 25%**；若超过 → 把非阻断项降为 `[P1]`/`[P2]`。禁止「几乎全是 P0」。  
- 自检口诀：去掉该条仍能走完主流程 → 不得标 P0。  

**溯源锚点（强制 · 供需求溯源台 · 路径优先）**
- 每条**交互叶子**句末追加：`〔源:入口或模块/目标页/区块 · 「关键控件」〕`  
- **定位顺序**：先页面路径（保证翻到对的页）→ 再区块（筛选区/列表区）→ 最后「」内控件  
- 路径里必须出现与溯源台图册页签一致的**目标页名**（如 `用户列表`、`工作台`）；禁止只写控件名  
- 路径段与①框架的 `##` / `###` 对齐，用 `/` 分隔；**不要写坐标**  
- 示例：
  ```
  - [P1] 在「用户账号」下拉选中一项后出现清除；点击清除恢复占位〔源:工作台/用户列表/筛选区 · 「用户账号」〕
  - [P1] 点击某行蓝色「联运币」弹出充值弹窗〔源:工作台/用户列表/列表区 · 「联运币」〕
  - [P0] 点击「用户列表」卡片，进入用户列表页〔源:工作台/联运管理入口区/用户列表〕
  ```
- 修订时保留已有 `〔源:…〕`；新增叶子必须补；禁止单独成行或写进标题行 

**每区块最小模板（有表单/列表/弹窗的 `###` 尽量齐）**
1. 默认态（含默认值写死）  
2. 合法操作成功（界面反馈写清）  
3. 取消 / 关闭 → 无副作用  
4. 空 / 非法 / 边界 ≥1（有输入时）  
5. （有列表）无数据缺省提示  

**分层与动词**
按「端/模块 → 页面 → 区块 → 断言」；顺序与框架一致（上→下、左→右）。
- **全覆盖（强制）**：框架有几个一级 `##`（如首页、祈福服务、商城、我的），功能点就必须有几个同名 `##`；禁止只写首页。  
- 首页入口挂载可写深链路，但**不要把所有细测只堆在首页下**导致输出截断、其余 Tab 缺失；Tab 本页（列表/筛选/下单/订单/个人中心）写在对应 Tab 的 `##` 下。  
- 首页推荐进入的详情：首页侧保留「进入 + 关键操作」；完整细测放在归属 Tab（如祈福服务 / 商城）下。
- **展示**：能显示〔具名控件〕…；（无数据）能显示缺省提示「…」  
- **操作**：点击「…」能弹出…；输入…后点「搜索」，列表仅…；点击「取消」关闭且不会…；点击「确定」关闭且会…  
- **校验失败**：须写清提示文案或阻断表现（不只写「不能提交」）  
- **控件**：单选/多选、分页、每页条数  

❌ 禁止：

**③ 易漏强制清单（有则必写，对齐专业评审）**
1. **仪表盘/工作台待办卡片**：抓取可见的每一张可点卡片（订单/售后/审核…）各 1 条 `[P0]`：点击 → 进入目标列表且默认对应该状态 Tab（勿只写其中一两张）。  
2. **侧栏/分组导航**：每个一级菜单进模块 1 条即可；有分组折叠则写「展开 + 点子菜单 → 页签出现」。  
3. **通用支付弹窗**：凡下单/预约/购买共用支付层 → 统一写「展示应付金额 / 取消关闭无扣款 / 确认后进成功态或留当前页」（可挂在首次出现的模块，他处引用「见支付弹窗」）。  
4. **资源用尽 / 次数为 0 弹窗**（福缘用尽、次数不足等）：入口触发 → 弹窗按钮闭环（去邀友/稍后再说/我知道了等）各写可观察结果。  
5. **成功弹窗主按钮闭环**：立即使用/确定/领取等必须写关弹窗/回某页/提示文案；禁止只写到「点击」。  
6. **多入口同页**：次要入口（如「我的→靓号管理」）至少 1 条可执行叶子，禁止只写「细测见××」而无断言。  
7. **详情页**：框架已列的详情字段区，进入后至少抽样关键字段可见性 + 关闭/返回；禁止只有「进入详情」。  
8. **售罄 / 限购 / 规格未选**：有态则写按钮置灰或提示，与正常下单成对。  
9. **配置空态界面**（无轮播、推荐为空、公告全下架）：③ 写界面表现；业务结果归②。  
10. **售后分流界面**：仅退款 vs 退货退款同意后底部按钮/进度文案须拆开写，禁止一条「或」盖两种。  

自检（③）：  
- 若框架一级 ## 在输出中缺失（例如有「祈福服务/商城/我的」却只有「## 首页」）→ 不合格，必须补全。  
- 若静态展示叶子明显多于交互叶子 → 不合格，删并合并。  
- 若出现「界面与原型一致」单独成条 → 改为点名控件或删除。  
- 若叶子是业务结果（扣次数/改订单态/入池）→ 挪到②。  
- 若无任何 `[P0]` → 补标；若 `[P0]` 占比 >25% → 降噪后重交。  
- 若还能问「选哪个选项？默认开还是关？点取消还是确定？」→ 继续拆。
- 若把「记录」才能进的页写到「立即使用」等其它按钮上 → 不合格。
- 成功弹窗主按钮必须有可观察闭环；有交互轨迹/可见演示时按演示写（可标【据原型演示】）；无证据则【待核实】，勿臆造目标页。
- 上述「易漏强制清单」有对应原型能力却整项缺失 → 不合格。

### 专项测试点写法（④ · 独立模块 · 可导入禅道）

④ **不写进**①②③正文，单独输出一份 Markdown。导入禅道时挂在顶层模块 **「专项测试」** 下（与「冒烟测试」「业务场景」、页面功能树并列）。

**何时必须出④（强制）**  
凡后台/管理端、含支付/审核/提交、多角色、或 C 端小程序/App —— **必须生成④**。纯静态展示页可写「本原型无明显专项风险」并仍保留五个 `##` 各 ≥1 条待核实或 N/A 说明叶子。

**结构（强制 · 五个一级 `##` 齐）**

```
# （项目名）· 专项测试点

## 权限与多角色
### （角色或能力名，如 运营 / 客服 / 只读 / 未登录）
- [P0] （条件）可观察结果
…

## 并发与幂等
### （场景名，如 支付提交 / 审核通过 / 抢号）
- [P0] （连点两次「提交支付」）只产生 1 笔有效订单，第二次提示处理中或已提交
…

## 弱网与异常网络
### 加载与提交
- [P1] （弱网）列表加载中展示加载态，失败能提示并可重试
…

## 兼容性
### 端与分辨率
- [P2] （常见机型/浏览器）主路径可完成，无遮挡关键按钮
…

## 安全
### 越权与敏感
- [P0] （无权限账号）直接访问管理 URL / 接口不能看到或操作他人数据
…
```

**各章最低覆盖（有对应能力则必写；无则写 1 条「本原型无××，跳过」并标 `[P2]`）**

| 章节 | 至少覆盖 |
|------|----------|
| 权限与多角色 | ①可见角色/菜单差异；②无权限隐藏或禁用；③越权打开他人详情/审核失败；④未登录访问需登录页的入口 |
| 并发与幂等 | ①支付/下单连点；②审核同意/驳回连点；③发货/核销连点；④抢名额/抢号连点；⑤重复提交表单 |
| 弱网与异常 | ①首屏/列表弱网加载与失败重试；②提交中断或超时提示；③上传失败可重试（有上传时） |
| 兼容性 | ①主端（小程序/H5/PC）主路径；②常见宽度下按钮可点、无遮挡（写具体端名，勿空写「兼容性良好」） |
| 安全 | ①越权读/写；②敏感操作需二次确认或验证（若原型有）；③XSS/脚本型输入不执行（有富文本/还愿/公告时）；④退出后返回不能继续操作 |

**写法约束**
- 叶子同样：`[P0/P1/P2]` + `（条件）` + 可观察结果；可直接当禅道用例。  
- ④ 写**专项风险**，不要重复抄③的普通点击路径；可引用模块名「在商城确认订单」。  
- 原型未给出多角色时：权限章按「已登录 / 未登录 / 说明中的角色」写，缺证据标【待核实】。  
- 禁止空话：「并发正常」「安全无问题」「兼容性 OK」。  
- 用例类型口径（导入禅道）：权限/安全 → 安全相关；弱网 → 性能测试；兼容 → 其他；并发幂等 → 功能测试。

自检（④）：五个 `##` 齐全；每章 ≥2 条叶子（或 1 条明确跳过说明）；P0 仅用于越权成功阻断、重复扣款/重复审核、支付连点等真风险。

### 评审闭环（可选）
有①/②/③/④后可点「评审」：对照原型输出合订报告（分①框架 / ②场景 / ③功能 / ④专项）。  
权威：交互轨迹 ≫ 可见正文 ≫ 说明。严重问题必须摘录证据；禁止「若无菜单则臆造」；多入口可并存；说明缺步但演示有结果却未写入 → ③遗漏；吃不准标「待核实」进建议改进。  
④ 重点查：五章是否齐、有无空话、支付/审核连点与越权是否覆盖。  
再点「按评审重生成」时，必须落实报告中对应章节的严重问题与遗漏，输出完整新版（不是补丁）。

### 业务场景测试点写法（② · 冒烟门禁 + 业务场景 · 双段输出）

② **不是**纯冒烟，也 **不是**页面功能细测。一次输出必须包含两段：

1. **`## 冒烟门禁`**：最短主链路（建议 ≤15 条），只问「通不通」，供提测/日构建闸门。  
2. **`## 业务场景`**（其下再按业务能力分 `###`）：条件 × 业务结果，验业务对不对。

**与①③、与冒烟的分工（强制）**

| 层级 | 问什么 | 叶子形态 |
|------|--------|----------|
| 冒烟门禁（② 第一段） | 主链路断没断？ | 短句「能进入… / 能完成…」 |
| 业务场景（② 第二段） | 条件 A/B 下结果对不对？ | `（条件）业务结果` |
| ③ 页面功能 | 点哪、文案、控件反馈 | 操作 + 界面断言 |

- ❌ 禁止把③塞进②：吸顶、背景音乐、弹窗按钮文案、勾选协议逐步剧本、筛选控件细则。  
- ❌ 禁止②第二段只写功能名词（如单独一行 `- 请分身` / `- 购物车`）——必须写成可判定的业务结果。  
- ❌ 禁止按「每一个 UI 页面」平铺一长列业务 `###`（购物车、支付成功、设置…若无独立业务规则可并入上级能力或留给③）。

**结构（强制双段）**

```
# （项目名）· 业务场景测试点

## 冒烟门禁
- （建议 ≤15 条）登录/进首页/核心主路径能走通…
- 不含规则矩阵、不含 UI 展示细节

## 业务场景
### （业务能力名，如 请分身 / 线上祈福 / 签到领福 / 商城下单）
- （条件）业务结果
- （另一条件）另一结果
```

1. 冒烟门禁：只保留 P0 骨架路径；失败即应打回。  
2. 业务场景一级分组用 **用户目标 / 业务能力**（请分身、福缘消耗、订单流转…），对齐框架里的业务入口，**不要**「一页一个分组」。  
3. **全覆盖**：框架各 Tab/模块下的主能力都要有对应 `###`（可按能力名合并，但不能整模块缺失）。  
4. 叶子句式：`[（前置条件）] + 会/不会/成功/失败/扣减/状态变为…`；金额、次数、开关写死。  
4. 只在有业务意义的状态处分叉；深度约 2～4 层。禁止登录注册写 5～6 层 UI 嵌套。  
5. 禁止「正向业务 / 逆向业务」两大章。  
6. 规则交叉（开关 × 同号/同证 × 多渠道）必须拆到可测叶子。  
7. **配置开关成对（强制）**：说明/抓取出现的业务开关，须同时覆盖「开」与「关」下的业务结果（如购买补充次数关闭且次数为 0 → 不能买/仅提示不足；添香火人民币 vs 祈福值）。只写默认开不够。  
8. **活动/期次边界**：有活动期、池抢完、下一期 → 分别写「池抢完」「活动已结束不可参与」（文案待核实可标）。  
9. **配置值为 0 / 空配置**：如签到某项填 0 不发放、无首页推荐时栏目空态等，有则单列。  
10. **后台↔客户端联动**：后台改公告/轮播/上下架/审核后，客户端可见性或状态须有对应业务叶子（可与冒烟区分，细节放业务 ###）。  

自检（②）：  
- 若框架有多个一级模块（如首页/祈福服务/商城/我的），业务场景却几乎只有首页相关能力 → 不合格，必须补齐各模块主能力。  
- 若无 `## 冒烟门禁` 或门禁超过约 15 条且夹杂规则矩阵 → 不合格。  
- 冒烟须覆盖：各主 Tab 可达 + 工作台/首页上**每一张可点待办/统计卡片**至少各 1 条跳转门禁（有则必写）。  
- 若叶子在讲按钮/文案/吸顶/音乐 → 挪到③。  
- 若叶子没有「会/不会/成功/失败/扣减/状态」且只是功能名 → 改写或删除。  
- 若还能问「开还是关？入不入池？」的规则交叉 → 继续拆。
- 若开关只写了开启态、未写关闭态 → 不合格。

## 具体数据（强制）
原型/设置里的默认金额、天数、开关、选项文案必须写进原文。  
禁止只写「阈值」「设定金额」；要写「最近 30 天流水低于 500 元」「未登录超过 15 天」。

### 第二步 · 业务场景测试点（冒烟门禁 + 业务场景）
按「写作风格 · 业务场景」**双段输出**：先 `## 冒烟门禁`（≤15 条主链路），再 `## 业务场景`（按业务能力分组，叶子必须是条件+结果）。  
**必须覆盖框架各一级模块下的主要业务能力/入口**（对照框架 ##、###、「进××」），禁止只写首页相关就结束；冒烟须串起各主 Tab 可达路径，并覆盖工作台/首页可点待办卡片。  
禁止逐步 UI、展示类细节（归③）；禁止「正向/逆向」两大章；禁止只写功能名词；禁止按每个 UI 页平铺。

### 第三步 · 页面功能测试点（测行为，少抄皮）
按框架顺序写操作与界面反馈；**≥70% 交互/校验/空态，≤30% 静态展示**；叶子标 `[P0]`/`[P1]`/`[P2]`，**P0≤25%**。  
**必须覆盖框架每一个一级 `##`**；落实「③ 易漏强制清单」（待办卡片、支付弹窗、用尽弹窗、成功闭环、多入口、详情字段、售罄限购、空态、售后分流）。  
禁止「界面与原型一致」空叶子；禁止逐商品抄价格；禁止业务结果型叶子（归②）；入口导航每入口最多 1 条。
