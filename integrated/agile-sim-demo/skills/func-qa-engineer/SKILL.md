# 功能测试工程师（工作台兼容）

与 `business-smoke-test` 分工：冒烟验主流程；本 skill 验**页面功能细项**是否真的在现网可定位/可交互。

必读配套：

1. 工作台：`workbench/skills/playwright-skill/SKILL.md`（或 Cursor 全局 `playwright-skill`）— 定位/断言黄金法则  
2. 本仓库跑测脚本：`integrated/agile-sim-demo/tests/business-automation/xinshangwu_func.spec.ts`  
3. 用例源：测试点生成「页面功能」markdown → 功能测试台同步  
4. 人工测录归档：`workbench/docs/func-sessions/`（按日期一篇）

## 人工测录 → 抽象 → 复现（核心闭环）

目标：用户上班手测一轮后，把过程描述给 Agent；Agent **抽象进本 skill / 测录文档 / Playwright 步骤**，之后能：

1. **复现测试过程**（同样角色、同样步骤、同样数据）  
2. **复现已报 Bug**（最小步骤 + 期望/实际 + 稳定前置）

### 用户怎么描述（尽量按这个发，缺项 Agent 先问再写）

每次手测结束，用自然语言即可，建议带上：

```text
【环境】URL / 账号角色（超管、一级商务…）
【页面】菜单路径或 URL（如 商务管理 → 商务列表）
【前置数据】用了哪个已有商务/渠道名；缺数据时你怎么造的（或「当时库里已有」）
【步骤】1. … 2. … 3. …（含：填了什么、点了什么）
【期望】列表应… / 提示应… / 指标应…
【实际】通过 or Bug：实际看到什么（可贴文案/截图说明）
【Bug 标签】（可选）阻塞/严重/一般；是否必现
```

口播、碎碎念也可以；Agent 负责整理成结构化测录。

### Agent 收到描述后必须做的事

1. **抽象成测录卡片**（写入 `workbench/docs/func-sessions/YYYYMMDD-<模块>.md`）  
2. **更新本 skill 的「已沉淀剧本」表**（下方），避免只存在聊天里  
3. **能自动化的**：改/补 `xinshangwu_func.spec.ts`（或独立 `*_repro.spec.ts`），步骤与断言对齐测录  
4. **Bug**：单独建「复现用例」——最小步骤、固定种子数据/账号、失败即红；不要混进「页面随便打开就算过」  
5. **回写功能测试台**：相关 F 用例的 hints/加深逻辑与测录一致；跑一轮证明能复现过程或复现 Bug

### 测录卡片模板（Agent 落盘用）

```markdown
## 测录 ID：FS-YYYYMMDD-XX
- 模块 / 页面：
- 角色 / 账号：
- 前置：
- 步骤：
  1.
  2.
- 期望：
- 实际：
- 结论：通过 | Bug
- Bug 摘要：（若有）
- 自动化：已写入 spec `...` / 待补
- 复现命令：（grep 用例 ID 或 npx 命令）
```

### 复现 Bug 的硬规则

- 先保证**前置数据可重建**（复用冒烟造数 / 写明种子账号 / 或 SQL 种子）；否则只记「人工必现、自动化阻塞：缺数」  
- 复现脚本断言对准 **Bug 的实际错误表现**（错误提示、错误列表行、错误指标），不是只 assert 页面打开  
- 修 Bug 后：同一脚本应变绿；保留为回归用例

## 判定标准（必须遵守）

| 细项类型 | 例子 | 未定位时 |
|---|---|---|
| **可见性断言** | 能显示、标题为、占位符、标签、列表列、开关 | **失败**（记 miss + 无区域图） |
| **交互断言** | 点击、输入、勾选、下一步、搜索 | 目标控件未找到 → **失败**；找到并完成一步 → 通过 |
| **数据样例** | 具体原型假数据「3,847」「待处理 5 条」 | **不因数值不一致失败**；控件/标题在则通过，记 note「样例数据以现网为准」 |
| **文案别名** | 原型「忘记密码」现网「找回密码」 | 用别名表匹配，匹配到算命中 |
| **人工测录步骤** | 用户描述的填搜/造数/对库 | 以测录为准；未实现自动化前不得假装已覆盖 |

用例级：

- 可见性细项 ≥ 3 条时，命中率 **&lt; 40% → 整条 F 用例失败**
- 命中率 40%～70% → 用例可标 **警告通过**（status=passed + note 含 WARN），优先修定位  
- 命中率 ≥ 70% 且关键加深步骤 OK → 通过  
- **已沉淀的人工测录剧本**：必须按步骤执行；失败 = 过程未复现或 Bug 仍在

不要再把「打开页面 + 侧栏有字」当成细项全过。

## 定位策略（吸收 playwright-skill）

优先级（高→低）：

1. `getByRole(button|textbox|checkbox|link|heading, { name })`
2. `getByLabel` / `getByPlaceholder`
3. `getByText`（短关键词，「」内文案优先）
4. 别名表（忘记密码↔找回密码，记住账号↔记住密码…）
5. 最后才 CSS；禁止裸 XPath

等待：用 `expect(locator).toBeVisible()`，禁止无意义的长 `waitForTimeout`。

## 区域截图

- 命中：元素截图 + 相对整页 box → 工作台悬停叠图  
- 未命中：status=miss，用例说明写清「哪条细项未定位」

## 在工作台执行

1. 项目中心 → 功能测试台 → 从测试点同步  
2. 一键功能测试（或 Agent `POST .../func/run`）  
3. 看细项命中率；未定位列表要进失败说明  
4. 人工测录复现：跑对应 `FS-` / repro 用例或 grep 剧本 ID  

Agent 加深时：先读本 skill + playwright-skill 的 locators/forms，再改 spec；**优先落地用户刚测过的剧本**，不要只放宽断言刷绿。

## 能力边界（诚实）

默认功能台脚本**不会自动**：走完整冒烟造商务/绑定、真搜索断言结果、查库验环比——除非：

- 用户测录要求如此，或  
- 已写入下方剧本并实现到 spec  

接到用户测录后，缺造数/对库能力时要明确写「阻塞项」，并尽量挂冒烟已有造数能力补齐。
