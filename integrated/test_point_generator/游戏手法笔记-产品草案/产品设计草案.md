# 游戏手法与个人策略笔记 — 产品设计草案（个人向 / MVP）

> 用途：给自己理清产品边界、对齐原型（Figma 等）与后续开发（可整段提供给 AI 作上下文）。

---

## 一、产品一句话

在多款游戏之间切换，为**队伍 / 流派 / 养成计划**保存「文字详解 + 步骤/时间轴」，下次游玩同一上下文时能**快速回忆并延续**自己的打法与计划。

---

## 二、用户场景（User Stories）

| 编号 | 场景 | 成功标准 |
|------|------|----------|
| S1 | 玩原神时，为某支队伍记下输出手法（含网上学的操作） | 能保存标题、可选版本、步骤列表与补充说明 |
| S2 | 隔几天再用同一支队伍开玩 | 能按「游戏 → 队伍」找到记录，打开后 1 分钟内上手流程 |
| S3 | 切换到另一款游戏 | 资料按游戏隔离，互不混淆；进入主流程后可在列表或切换器选游戏 |
| S7 | 打开应用时有个性化封面 | 用户可上传/更换一张图作为首页封面；首访可用默认占位图 |
| S4 | 同一游戏多条记录 | 能区分不同队伍、不同流派或不同「备忘类型」（手法 / 培养计划） |
| S5 | 离线使用（可选 MVP） | 首版若本地单机，不依赖网络亦可增删改查 |
| S6 | 日后接 AI（可选） | 数据结构清晰、单条记录可导出为纯文本/Markdown，便于投喂模型 |

---

## 三、名词与范围（MVP 内）

- **游戏**：顶层分类，例如「原神」「另一款 RPG」。
- **条目**：一条独立笔记，类型可为 `输出手法` | `培养计划` | `通用备忘`（首版可先只做前两种 + 通用）。
- **队伍/标签**：用于「同一支队伍」的稳定检索；建议结构化字段 + 简短别名，避免只靠长文标题。
- **步骤**：有序列表，可选「相对时间/秒数」字段，用于时间轴式招式；无时长则退化为纯步骤。

---

## 四、页面列表与职责

| 页面/屏 | 职责 | 主要操作 |
|---------|------|----------|
| P1 封面首页 | 全屏/主体区域展示**用户上传的封面图**；视觉焦点为**居中主按钮** | 点击主按钮 → 进入 **P2 游戏列表**；可选「更换封面」上传本地图片 |
| P2 游戏选择 | 维护游戏列表、选中「当前游戏」 | 添加/重命名/删除游戏（删除需二次确认）；选游戏后进入该游戏 **P3 条目列表** |
| P3 条目列表（某游戏下） | 该游戏下所有条目，支持筛选 | 按类型/标签筛选、排序（更新時間、标题）、点击进入详情 |
| P4 条目详情 / 阅读模式 | 专注阅读步骤与说明，可选「演练模式」逐条高亮（可后置） | 编辑、复制全文、分享导出（可后置） |
| P5 条目编辑 | 编辑元数据 + 富文本或 Markdown + 步骤列表 | 保存、放弃、删除条目 |
| P6 设置（可后置 MVP+） | 主题、语言、数据导出/导入路径、关于 | 导出 JSON/Markdown 备份；可收录封面设置或置于 P1 内轻量入口 |

**首版可先实现**：P1～P5；P6 可用「导出文件」代替完整设置页。

**P1 补充说明**：封面图为**个人本地偏好**，不必然与某一游戏绑定；无图时可使用纯色或内置占位图。主按钮文案示例：「进入笔记」「开始使用」等，与品牌一致即可。

---

## 五、核心用户流程（简）

1. 打开 App → **P1 封面首页**（展示已保存的封面图或占位）→ 点击**中间主按钮** → **P2 游戏列表**。
2. 游戏列表选中当前游戏 → **P3 条目列表** → **新建条目** → 填队伍名、类型、版本、步骤 → 保存。
3. 列表中找到条目 → **P4 详情** → 边玩边看步骤。
4. 切换游戏：从列表返回或通过导航进入游戏列表 / 切换当前游戏 → 另一游戏的条目列表。

## 六、数据模型 — 字段说明（建议）

### 6.0 应用本地偏好 `AppPreferences`（可选，与后端无关时仅存浏览器/客户端）

| 字段 | 类型 | 说明 |
|------|------|------|
| `home_cover_image` | string? | 封面图：**base64（data URL）** 或 **本地持久化后的 blob/路径**（按实现选型）；无则 UI 用占位 |
| `home_cover_updated_at` | string? | ISO 8601，可选 |

*Web MVP 常见做法：`localStorage` 存 data URL（注意大图体积）或 IndexedDB 存 Blob；若顾虑配额，可仅存用户最后一次选择的文件名 + 提示「刷新后需重选」——首版可选。*

### 6.1 游戏 `Game`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string (UUID) | 主键 |
| `name` | string | 显示名称，如「原神」 |
| `sort_order` | number | 列表排序，可选 |
| `created_at` / `updated_at` | ISO 8601 | 可选 |

### 6.2 条目 `Entry`（隶属于某 Game）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string (UUID) | 主键 |
| `game_id` | string | 外键 → Game |
| `title` | string | 条目标题，如「胡行钟夜 - 深渊循环」 |
| `entry_type` | enum | `rotation`（输出手法） / `build_plan`（培养计划） / `note`（通用） |
| `team_name` | string | 队伍名或标签，用于检索（可与 `title` 不同） |
| `character_tags` | string[] | 可选，角色名或标签，如 `["胡桃","行秋","钟离","夜兰"]` |
| `game_version` | string? | 可选，游戏版本或补丁纪年，如「5.x」或「2026-05」 |
| `summary` | string? | 可选，一句话摘要，列表展示用 |
| `body` | string | 正文：详解；建议 Markdown 或可降级为纯文本 |
| `steps` | `Step[]` | 见下表 |
| `source_links` | string[]? | 可选，参考链接 |
| `pinned` | boolean | 是否置顶，可选 |
| `last_opened_at` | datetime? | 用于「最近使用」，可选 |
| `created_at` / `updated_at` | ISO 8601 | 建议必有 |

### 6.3 步骤 `Step`（内嵌于 Entry）

| 字段 | 类型 | 说明 |
|------|------|------|
| `order` | number | 从 0 或 1 递增 |
| `label` | string | 简短动作名，如「夜兰 Q」 |
| `detail` | string? | 该步补充说明 |
| `offset_sec` | number? | 可选，相对时间轴秒数（无则仅有序列表） |
| `duration_sec` | number? | 可选，持续时长 |

### 6.4 本地存储（实现时参考）

- 单机 MVP：`SQLite` / `JSON 文件` / `LevelDB` 等择一；导出为 JSON 或 Markdown 包便于备份与 AI 使用。

## 七、非功能需求（首版建议）

- **性能**：单游戏数百条条目内检索流畅（标题/队伍名关键词即可）。
- **隐私**：默认本地；若未来云同步，需单独设计加密与账号。
- **可移植**：字段稳定后少改列名，避免升级丢数据。

## 八、待决问题（实现前尽量拍板）

1. 首版是否必须 **「时间轴 UI」**，还是 **有序列表 + 可选秒数** 即可？
2. 是否需要 **截图/附件**（会显著增加复杂度）？
3. **「同一支队伍」** 是否强制 `character_tags` 排序归一化，避免重复条目？
4. 平台：桌面（Win）优先还是 Web / 移动？
5. 是否第一版就做 **全局搜索**（跨游戏），还是只做游戏内搜索？
