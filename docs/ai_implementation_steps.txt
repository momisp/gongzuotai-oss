个人工作台后续 AI 实施方案

一、项目目标

这个项目是个人工作台，用于提升测试工程师兼运维工作的日常效率。

核心目标：
1. 快速查找常用文件、目录、项目和脚本。
2. 整合测试、压测、测试点生成、Bug 数据、报告生成等工具。
3. 分类管理常用网址，明确每个网址适合解决什么问题。
4. 提供常用数据转换工具，例如 Base64、时间戳、时间转换、JSON 格式化。
5. 支持后续继续扩展新功能，新增功能时尽量少改主代码。

重要约束：
1. 不要修改原始项目和脚本目录。
2. 必须先复制一份到当前工作台项目内，再基于副本整合。
3. 用户数据、配置数据、收藏数据要放在工作台自己的 data 目录中。
4. 第一版优先做简单可用，不要过度设计。
5. 代码应遵循 KISS 原则，函数优先，直接实现，避免复杂抽象。

四、后续 AI 的执行顺序

步骤 1：确认当前目录

确认当前工作目录是：
.

不要在原始路径中直接改代码。

步骤 2：创建基础目录

创建以下目录：
1. workbench
2. integrated
3. data
4. docs

步骤 3：复制外部项目和脚本

将原始路径复制到 integrated 目录。

复制规则：
1. 如果目标目录不存在，直接复制。
2. 如果目标目录已存在，先询问用户是否覆盖、跳过或另存为带日期的目录。
3. 不要删除原始路径下的任何内容。
4. 不要移动原始路径，只能复制。

步骤 4：识别可复用项目

检查 integrated\game_notes_web 是否是前端项目。

如果它适合作为工作台基础：
1. 在 integrated\game_notes_web 的副本上开发。
2. 或复制一份到 workbench 作为主项目。
3. 不要直接改桌面上的原始 game-notes-web。

如果它不适合作为工作台基础：
1. 在 workbench 下新建一个简单 Web 项目。
2. 只把已有项目作为工具入口或功能模块接入。

步骤 5：第一版先做首页

首页只需要包含以下入口：
1. 文件路径收藏
2. 常用网址收藏
3. 数据转换工具
4. 测试报告生成
5. 压测工具入口
6. 测试点生成入口
7. 运维常用命令入口

第一版不要追求复杂权限、数据库、登录系统。
本地个人使用时，优先使用 JSON 文件保存配置。

步骤 6：实现文件路径收藏

数据文件：
data\file_paths.json

建议字段：

[
  {
    "id": "performance-scripts",
    "name": "压测脚本目录",
    "path": "integrated\\performance",
    "type": "directory",
    "category": "压测",
    "tags": ["性能测试", "脚本"],
    "note": "存放常用压测脚本和压测数据"
  }
]

功能要求：
1. 支持新增路径。
2. 支持编辑备注。
3. 支持按名称、分类、标签、备注搜索。
4. 支持一键打开目录或复制路径。

步骤 7：实现常用网址收藏

数据文件：
data\links.json

建议字段：

[
  {
    "id": "online-bug-doc",
    "name": "线上 Bug 文档",
    "url": "https://example.com",
    "category": "Bug 文档",
    "problem": "查看线上已知问题和历史处理记录",
    "tags": ["Bug", "线上问题", "排查"]
  }
]

功能要求：
1. 支持新增网址。
2. 支持分类。
3. 每个网址必须写清楚能解决什么问题。
4. 支持搜索问题描述，例如 查日志、看监控、查接口、提 Bug。

步骤 8：实现数据转换工具

第一版内置以下工具：
1. Base64 编码
2. Base64 解码
3. 时间转时间戳
4. 时间戳转时间
5. JSON 格式化
6. URL 编码
7. URL 解码

实现要求：
1. 每个工具独立成简单函数。
2. 输入框、输出框、复制按钮即可。
3. 不需要复杂历史记录。

步骤 9：实现测试报告生成

第一版先支持手动输入或粘贴数据，生成 Markdown 或 HTML 报告。

报告类型：
1. 测试报告
2. 性能测试报告
3. Bug 率统计报告

数据来源优先考虑：
1. integrated\test_point_generator
2. integrated\performance
3. integrated\test_tool

模板配置文件：
data\report_templates.json

第一版不要强行解析所有老项目，先保留入口和模板生成能力。

步骤 10：实现测试和运维工作区

建议增加一个 测试运维 区域。

包含：
1. 常用环境地址
2. 常用日志路径
3. 常用服务器命令
4. 发布检查清单
5. 线上问题排查步骤
6. 数据库、Redis、消息队列等排查入口

常用命令保存到：
data\commands.json

注意：
不要在 JSON 中明文保存密码、Token、密钥。

步骤 11：实现扩展机制

使用 data\tools.json 注册功能入口。

示例：

[
  {
    "id": "base64",
    "name": "Base64 工具",
    "category": "数据转换",
    "entry": "builtin:base64",
    "enabled": true
  },
  {
    "id": "performance",
    "name": "压测工具",
    "category": "测试工具",
    "entry": "integrated\\performance",
    "enabled": true
  }
]

后续新增工具时：
1. 新增一个页面、脚本或入口。
2. 在 tools.json 中注册。
3. 首页根据 tools.json 自动展示。

五、功能优先级

P0：必须先完成
1. 创建目录结构。
2. 复制原始项目和脚本到 integrated。
3. 建立首页。
4. 建立 data\tools.json。
5. 建立文件路径收藏。
6. 建立常用网址收藏。
7. 建立基础数据转换工具。

P1：第二阶段完成
1. 报告模板生成。
2. 测试点生成入口。
3. 压测工具入口。
4. Bug 率统计报告。
5. 运维命令收藏。

P2：后续扩展
1. 自动读取压测结果。
2. 自动生成测试报告。
3. 接入更多测试脚本。
4. 增加搜索高亮。
5. 增加备份和导入导出。

六、建议技术路线

如果 integrated\game_notes_web 是可运行前端项目：
优先复用它的技术栈作为工作台前端。

如果没有合适基础：
建议用简单 Web 技术实现：
1. 前端：HTML、CSS、JavaScript，或项目已有框架。
2. 数据：本地 JSON 文件。
3. 后端：如果需要打开本地文件或执行脚本，再增加轻量本地服务。

第一版不要上数据库。
第一版不要做复杂用户系统。
第一版不要做远程部署。

七、验收标准

第一版完成后，应满足：
1. 打开工作台能看到所有主要功能入口。
2. 能搜索常用文件路径。
3. 能搜索常用网址，并知道每个网址解决什么问题。
4. 能进行 Base64、时间戳、JSON 格式化等转换。
5. 能看到已复制整合的测试、压测、测试点项目入口。
6. 所有原始路径没有被修改。
7. 新功能可以通过 tools.json 继续扩展。

八、风险提醒

1. 复制项目时要避免覆盖已有副本。
2. 测试点生成目录和 game-notes-web 可能存在包含关系，复制前要确认。
3. 运维相关数据不要保存敏感密码。
4. 如果需要执行脚本，必须明确脚本来源和执行参数，避免误操作。
5. 工作台应优先服务个人效率，不要一开始做成大型平台。

九、给后续 AI 的一句话指令

请基于当前文件的方案，从创建目录结构和复制 integrated 副本开始实施。所有原始路径只能读取和复制，不允许直接修改。第一版优先完成首页、路径收藏、网址收藏、数据转换工具和工具注册机制。
